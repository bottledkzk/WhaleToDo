## 1. 目标与非目标

### 目标

1. 多设备可用：同一账户在 A/B 设备上都能读到同一份任务、安排、签到、可用时间与设置。
2. 离线可用：本地写入不等待网络；断网/进程被杀后 outbox 仍可恢复并幂等重试。
3. 冲突可见：版本冲突不静默覆盖用户输入；服务端当前值和本地待推送值都可展示、可选择。
4. 访客数据可合并：访客记录在用户明确确认后归入账户，不重复创建。
5. 账户隔离：所有同步读写、缓存、worker、游标和 outbox 都按 owner 分区；A 的迟到结果不能写入 B。
6. 幂等不重复：批次、对象创建、删除和 checkin 重复提交不产生重复记录或重复通知。

### 非目标

- 实时协作、多人同时编辑同一对象的 OT/CRDT。
- 服务端全文搜索、跨账户共享、公开链接。
- AI 会话/消息/日记正文的云端同步（本轮；见 §2 的边界决定）。
- 服务端 schema、RLS、迁移或部署变更；这些属于数据库负责人的独立 PR。
- 客户端通知的云端重放；提醒仍由本地最终状态驱动。

## 2. 现状与缺口

### 服务端已有能力

| 能力 | 现状 | 客户端影响 |
| --- | --- | --- |
| `POST /sync/push` | Bearer 登录；`batch_id` UUID、`device_id` ≤64；单批 1..200 项；每项 payload 前置上限 32KiB | 批次必须可重放，body 不可在重试时改变 |
| 对象类型 | `task`、`block`、`checkin`、`availability`、`settings` | 只有这五类可作为服务端对象 |
| 操作 | `create`、`update`、`delete` | 新建 `expected_version=null`；更新/删除必须带当前服务端版本 |
| 版本 | `sync_changes` 按对象追加 `version`；`decideMutation` 对版本不一致返回 `conflict` | 客户端必须保存每对象 `server_version`，不能只存“已同步”布尔 |
| 幂等 | `sync_batches(user_id,batch_id)` 唯一；同 batch 同内容返回原回执，异体 409；`sync_mutations` 记录结果 | 同一批重试必须复用同一个 `batch_id` 和同一 body |
| 结果 | 整批 `applied|partial|rejected`；逐项 `applied|conflict|rejected` | 按 item 更新 outbox，不能整批重放 |
| 拉取 | `GET /sync/pull?cursor=&limit=`；按 `seq` 升序；`next_cursor`、`has_more` | 游标是服务端变更序列，不是对象版本 |
| 删除 | `sync_changes.deleted=true` | 客户端需要 tombstone 防止旧副本复活 |
| 安全 | 内容表 RLS + 事务内 `set_config('app.user_id')`；批次串行化 | 客户端不得提交 owner/user_id；服务端从 Bearer 取身份 |

已确认的边界：服务端**不解释** payload 内部业务字段。`sync_changes` 保存客户端的 JSON，
服务端只校验对象类型、UUID、操作、版本、大小和事务/RLS。因此本文的 payload 字段是
**客户端提议的契约**；服务端当前按 opaque JSON 存储，不校验这些内部字段。

### 客户端现状

- Room 版本 4，已有 `tasks`、`blocks`、`checkins`、`settings`、`daily_work_times`，
  以及按 owner 分区的 `task_reminders`、`diaries`、`ui_preferences`、agent 表。
- `tasks`/`blocks`/`checkins`/`settings`/`daily_work_times` **没有 owner_id**；
  目前是单工作区模型，不能直接承担多账户隔离。
- 没有 outbox、没有服务端版本列、没有 cursor、没有 tombstone、没有冲突表。
- `DeskRepository` 的写入直接落 Room；没有“本地事务 + outbox”边界。
- T31 已引入 `AccountSession.sessionId`、`currentSessionId()` 和代次 guard；
  同步必须复用，而不是另建账户代次。

### 缺口决定

| 缺口 | 决定 | 理由 |
| --- | --- | --- |
| `task_reminders` | **本轮不同步，本地-only** | 服务端白名单没有该类型；通知是设备本地 AlarmManager 行为，跨设备同步会产生重复通知；T26 已按 owner 本地隔离 |
| `diaries` | **本轮不同步，本地-only** | 服务端白名单没有该类型；日记正文隐私等级更高，需要单独的数据最小化/加密评审；AI 日记不是同步对象 |
| `ui_preferences` | **本轮不同步，本地-only** | 主题、设备时区、星期偏好是设备/本地 UA 偏好；本轮 settings 只映射 `SettingRow` 的作息设置，避免把设备偏好混入账户设置 |
| agent 会话/消息 | **本轮不同步** | 与 AI 历史同步无关，且包含提示词/答复正文；另立隐私与保留期设计 |
| 未来 reminders/diaries 入白名单 | **另开服务端 PR**：新增白名单、RLS 字段、payload 约束、冲突规则和隐私评审后再进同步 | 不在客户端设计里偷跑服务端字段；不能把本地表直接当已支持 |

所以本设计的同步白名单严格为：
`task`、`block`、`checkin`、`availability`、`settings`。其余数据留在本地，后续单独设计。

## 3. 对象映射与本地数据模型

### 3.1 通用规则

- `object_type` 使用服务端枚举；`object_id` 必须是 UUID（服务端强制）。
- 客户端不发送 `owner_id`/`user_id`；owner 只存在本地授权上下文和服务端 Bearer 中。
- `payload` 为客户端 JSON；服务端按 opaque JSON 存储，不校验字段。字段名一次冻结后，
  客户端升级必须兼容旧 payload。
- 每个 payload 带 `payload_version`（当前 `1`）。未知版本不猜测、不覆盖本地：进入
  `conflict/failed` 并记录稳定错误码；未知字段默认忽略并记录字段名（不含值），
  类型非法或必填字段缺失则拒绝该对象，不把它写成部分对象。
- 所有瞬时时间使用 **epoch millis（UTC）**；业务日期使用 `YYYY-MM-DD` 字符串；
  本地墙钟时间使用分钟或小时整数，并附 IANA `time_zone`。
- 每对象本地新增：
  - `owner_id TEXT NOT NULL`：`guest` 或账户 userId；
  - `client_id TEXT`：稳定客户端 UUID；为空表示本轮不具备同步资格（例如旧非 UUID 主键）；
  - `server_version INTEGER NOT NULL DEFAULT 0`：0 表示尚未在服务端建立；
  - `updated_at INTEGER NOT NULL`：本地最后修改毫秒；只用于 UI/排序，不作为冲突胜负依据。
- `WHALETODO_SYNC_NAMESPACE` 固定为 `b420822a-ec70-4d54-976d-586dde231c6d`；实现时冻结并提交
  `settings`/`availability` 的 UUIDv5 测试向量。不得使用随机值、设备 ID 或 guest owner 作为
  namespace；变更 namespace 视为破坏性协议变更。
- 不使用对象级 `deleted` 布尔列；删除用 `sync_tombstones` 表达（§3.4）。

### 3.2 五类对象的 Room 映射

#### `task`

| 本地列/来源 | payload 字段 | 说明 |
| --- | --- | --- |
| `id` | 不放入 payload | 作为 `object_id`；必须 UUID |
| `title` | `title` | 去首尾空格；非空；长度按现 UI 约束 |
| `minutes` | `minutes` | 分钟；0..525600 |
| `deadline` | `deadline` | epoch millis；**0 表示无截止** |
| `importance` | `importance` | 1..5 |
| `done` | `done` | 布尔；受保护字段 |
| `created` | `created` | epoch millis |
| `note` | `note` | 文本；可空字符串 |
| `chunkMinutes` | `chunk_minutes` | 分钟 |
| `splittable` | `splittable` | 布尔 |
| `category` | `category` | `none/study/exercise/entertainment/work/social/travel/rest` |

- `locked` 不在 task；锁定属于 block。
- 新任务 `id` 生成 UUID；旧数据若主键不是 UUID，`client_id=null`，保留本地但不推送，
  升级报告列出数量，待修复后再参与同步。

#### `block`

| 本地列 | payload | 说明 |
| --- | --- | --- |
| `id` | 不放入 payload | `object_id` |
| `taskId` | `task_id` | 必须同 owner 的任务 |
| `start`/`end` | `start`/`end` | epoch millis；`end > start` |
| `locked` | `locked` | 手动锁定；受保护字段 |
| `done` | `done` | 受保护字段 |

- 一个 block 对应一个对象；自动排程生成的 block 与手动 block 使用同一对象类型。
- 修改 block 必须保留时长约束；与 `locked/done` 的冲突不自动覆盖。

#### `checkin`

| 本地列 | payload | 说明 |
| --- | --- | --- |
| `id` | 不放入 payload | `object_id` |
| `taskId` | `task_id` | 同 owner 任务 |
| `completedAt` | `completed_at` | epoch millis |
| `rating` | `rating` | 1..5 |

- checkin 是**追加型**对象：只 create，不 update/delete。
- 同 `object_id` 已存在且 payload 相同 → 视为已应用；payload 不同 → conflict，不覆盖。

#### `availability`

| 本地列 | payload | 说明 |
| --- | --- | --- |
| `date` | `date` | 本地业务日 `YYYY-MM-DD` |
| `startMinute`/`endMinute` | `start_minute`/`end_minute` | `start_minute` 0..1439，`end_minute` 1..1440，`end > start`；1440 表示当天结束 |
| `timeZone`（新增） | `time_zone` | IANA；迁移后为 NULL 的行在用户首次修改时补当前 zone |
| `clientId`（新增） | 不放入 payload | 目标 canonical UUIDv5：`UUIDv5(WHALETODO_SYNC_NAMESPACE, "availability:"+owner_id+":"+date)`；owner 为账户 userId |

- `availability` 的自然键是 `(owner_id,date)`；服务端对象 ID 使用目标 owner 的确定性 UUIDv5，
  避免“date 不是 UUID”而无法 push。
- `availability.end_minute=1440` 合法，表示当天结束；不能用统一的 0..1439 上限。
- 不同时区的同一日期不可自动合并；payload/本地行的 `time_zone` 不同即视为冲突候选。

#### `settings`

| 本地列 | payload | 说明 |
| --- | --- | --- |
| `id`（固定 1） | 不放入 payload | 每 owner 一个 settings 对象 |
| `startHour`/`endHour` | `start_hour`/`end_hour` | 本地墙钟小时；`0 <= start < end <= 24` |
| `timeZone`（新增） | `time_zone` | IANA；NULL 时本轮不自动推送，避免猜测 |
| `clientId`（新增） | 不放入 payload | 目标 canonical UUIDv5：`UUIDv5(WHALETODO_SYNC_NAMESPACE, "settings:"+owner_id)` |

- `settings` 只映射 `SettingRow` 的作息设置，不包含 `ui_preferences` 的主题/设备时区/星期偏好；
  后者本轮本地-only（§2）。
- `settings` 的自然键是 `(owner_id)`；目标 owner 为账户 userId 时使用 canonical UUIDv5，
  guest 合并时不得保留 guest 派生 ID。
- 当 `time_zone` 为 NULL 时，本地仍可用，但该 settings 不进入 outbox，直到用户显式选择/修改
  时区（避免 A 设备用 Asia/Shanghai、B 设备用 Europe/Berlin 静默覆盖）。

### 3.3 本地同步结构（设计，不在本任务建表）

#### `sync_outbox`

| 列 | 类型/约束 | 说明 |
| --- | --- | --- |
| `op_id` | TEXT PK | 每次本地变更的 UUID |
| `owner_id` | TEXT NOT NULL | `guest` 或账户 userId |
| `object_type` | TEXT NOT NULL | 五类白名单 |
| `object_id` | TEXT NOT NULL | 服务端 UUID；settings/availability 合并后为 canonical UUID |
| `op` | TEXT NOT NULL | `create/update/delete` |
| `payload_json` | TEXT | create/update 的规范化 JSON；delete 为 NULL |
| `base_version` | INTEGER | create 为 NULL；后继 update/delete 在收到前驱回执前为 NULL（未知） |
| `idempotency_key` | TEXT NOT NULL | 本地去重键；默认等于 `op_id`，不发送给服务端 |
| `parent_op_id` | TEXT | 同对象前驱意图；NULL 表示对象意图链的根 |
| `is_head` | INTEGER NOT NULL DEFAULT 1 | 当前链头；新写入只追加/合并到 head |
| `batch_id` | TEXT | 入批时与批次快照同一事务写入；**之后不可变**；未入批为 NULL |
| `state` | TEXT NOT NULL | `pending/inflight/blocked/done/conflict/failed` |
| `attempts` | INTEGER NOT NULL DEFAULT 0 | 已尝试次数 |
| `next_retry_at` | INTEGER NOT NULL DEFAULT 0 | epoch millis；0 表示可立即重试 |
| `created_at` | INTEGER NOT NULL | epoch millis |
| `last_error_code` | TEXT | 最近一次稳定错误码/原因，不含 payload |

约束与索引：

- 不再使用 `UNIQUE(owner_id, object_type, object_id) WHERE state='pending'`；后继意图要求
  同一对象允许多行。
- `UNIQUE(owner_id, object_type, object_id) WHERE is_head=1`（SQLite partial index）：
  每个对象最多一个链头；追加后继时在同一事务把旧 head 的 `is_head` 置 0。
- `(owner_id, state, next_retry_at)` 索引用于 worker 选批；
- `(owner_id, batch_id)` 索引用于进程重启后找回同批；`parent_op_id` 索引用于释放后继。

`batch_id` 是超出服务端字段列表的**本地持久化列**，原因是服务端只按 batch 幂等；
进程在“请求已提交、响应丢失”时，必须用同一 `batch_id` 重试，不能新造批次把同一批再发一次。
`batch_id` 一旦非空，原意图的 `payload_json/object_id/op/顺序` 都不可再改；后续修改只能追加后继意图。

#### `sync_batches`（不可变批次快照）

| 列 | 类型/约束 | 说明 |
| --- | --- | --- |
| `batch_id` | TEXT PK | 服务端幂等键；生成一次，重试复用 |
| `owner_id` | TEXT NOT NULL | 冻结的 owner；不得跨 owner 复用 |
| `created_session_id` | TEXT NOT NULL | 创建批次时的 T31 会话代次，永久审计；不可改 |
| `attempt_session_id` | TEXT | 本次发送/恢复尝试绑定的有效 sessionId；初始等于 created_session_id，恢复时只改本列，不改变 created_session_id |
| `device_id` | TEXT NOT NULL | 安装级 UUID |
| `body_json` | TEXT NOT NULL | **原样**发给服务端的规范 JSON（含 mutations 顺序/内容） |
| `body_sha256` | TEXT NOT NULL | body_json 的 UTF-8 SHA-256；仅用于诊断/异体检测 |
| `created_at` | INTEGER NOT NULL | epoch millis |
| `state` | TEXT NOT NULL | `prepared/sending/retryable/unknown/session_wait/recovering/applied/partial/rejected/invalid` |
| `attempts` | INTEGER NOT NULL DEFAULT 0 | 已发送次数 |
| `last_attempt_at` | INTEGER | epoch millis |
| `last_error_code` | TEXT | 稳定错误码，不含 payload |

状态机（发送侧）：

```text
prepared ──发送──> sending ──回执──> applied / partial / rejected
    │                  │
    │                  ├─429/5xx/超时──> retryable ──同一 body──> sending
    │                  ├─进程被杀/丢响应──> unknown ──同一 body──> sending
    │                  └─同 batch 异体 409──> invalid（不自动换 body）
    └─(owner,sessionId) 不匹配──> session_wait
                                      │
                                      └─同 owner + 用户确认──> recovering
                                            （attempt_session_id=当前 s2）
                                            └──postAsSession 同一 batch/body──> sending
```

- `prepared`：快照已提交、尚未发出；进程重启可继续用同一 body 发送。
- `sending`：HTTP 已发起；进程重启视为 `unknown`，不得推断原 create “没发出”。
- `retryable`：网络/429/5xx；只重试同一 `body_json`，不重新选批/重新序列化。
- `unknown`：响应丢失或进程在 `sending` 中死亡；用同 `batch_id` + 同 body 重发，服务端按 batch 回执。
- `session_wait`：当前 `sessionId` 与批次尝试值不一致；不发 HTTP，不用 B 的 Bearer 重发。
  批次保留 `created_session_id` 审计值，等待同 owner 显式恢复；不同 owner 永久不能接手。
- `recovering`：同 owner 且用户确认恢复后，记录本次 `attempt_session_id`（新 s2），
  batch_id/body/owner/created_session_id 不变；随后用同一 batch/body 调 `postAsSession`。
  恢复请求失败可回到 `session_wait/retryable` 再试，**不标 invalid、不重造 body**。
- `invalid`：同 batch 异体/指纹不符/协议错误；保留快照供诊断，不自动新造批次。
- `applied/partial/rejected` 是终态；批次快照保留，便于审计和定位后继意图。
- 选批、写快照、给 outbox 行写 `batch_id`/`inflight` 必须在**同一个 Room 事务**中完成；
  提交前不得发 HTTP。

| `deleted_at` | 毫秒 |
| `version` | 删除后的服务端版本 |
| PK | `(owner_id, object_type, object_id)` |

#### `sync_id_mappings`

只用于 guest→账户合并时**自然键对象**的 ID 映射；task/block/checkin 保留原 UUID，不写映射。

| 列 | 说明 |
| --- | --- |
| `owner_id` | 合并后的账户 userId |
| `object_type` | `settings` / `availability` |
| `guest_object_id` | guest 派生 UUID（本地-only，不发送） |
| `account_object_id` | 账户 canonical UUIDv5 |
| `natural_key` | 规范化自然键（`settings:<owner>` 或 `availability:<owner>:<date>`） |
| `created_at` | 毫秒 |
| PK | `(owner_id, object_type, guest_object_id)` |

映射用于诊断、幂等重试和防止重复合并；不把 guest ID 发送给服务端。合并时为 guest 对象写
`owner_id='guest'` 的 tombstone（version=0，本地-only），见 §7.2。

#### `sync_conflicts`

冲突不能只留一个错误码；需要保留双方数据供 UI：

| 列 | 说明 |
| --- | --- |
| `owner_id` / `object_type` / `object_id` | 对象 |
| `local_payload_json` | 发起冲突的本地 payload |
| `remote_payload_json` | 冲突拉取得到的服务端 payload（无 payload 时为 NULL） |
| `local_base_version` / `server_version` | 版本 |
| `reason` | `version_mismatch/already_exists/not_found/remote_deleted/...` |
| `created_at` | 毫秒 |
| `state` | `open/resolved` |

### 3.4 删除表达

- 选择 **tombstone**，不给每张内容表加 `deleted` 列。
- 本地删除在**同一 Room 事务**中：删除内容行 + 写 `sync_outbox(op=delete, payload=NULL,
  base_version=server_version)` + 写/更新 `sync_tombstones`（版本用当前 `server_version`，
  服务端确认后回填新版本）。
- pull 到 `deleted=true`：写 tombstone，删除本地内容行；不把旧 payload 重新插入。
- 客户端收到 `version <= tombstone.version` 的旧 create/update 时直接丢弃；大于 tombstone.version
  的变更才允许恢复。
- 删除**已入批但尚未确认**的 create：不能删除原 outbox，也不能撤销原批；在同一事务中
  删除/隐藏本地内容行、写本地 tombstone（version=0）、追加 `op=delete` 的后继意图，
  `base_version=NULL`、`state=blocked`、`parent_op_id=原 create`。
  - 原 create 回执 `applied` 或批级 `replayed`（未来兼容 `item duplicate`）后，把后继 delete 的
    `base_version` 设为回执版本并发送；
  - 原 create 明确 `rejected` 且服务端未接纳，取消后继 delete（无服务端对象），本地 tombstone 保留；
  - 原 create 状态 `unknown` 时只重试原批/查询/拉取，不发送 delete，也不因 pull 到对象而复活本地。
- 删除**已入批的 update**：同样追加后继 delete，等 update 回执确定版本后再发；不得把原
  update 行改写成 delete。

### 3.5 Room 版本与迁移

当前 `DeskDatabase` 为 **version 4**；目标为 **version 5**，只增表/列并重建需要复合主键的表。

- 五张内容表增加 `owner_id`、`client_id`、`server_version`、`updated_at`；
  `settings`/`daily_work_times` 增加可空 `time_zone`。
- 主键调整：
  - `tasks`、`blocks`、`checkins`：`(owner_id,id)`；
  - `settings`：`(owner_id,id)`（id 仍为 1）；
  - `daily_work_times`：`(owner_id,date)`。
- 因为 SQLite 不支持直接改主键，迁移采用“建新表 → 复制 → 校验计数/外键引用 → drop 旧表 →
  rename”的受控重建；全程在一个事务中，失败回滚。
- 旧数据：
  - `owner_id='guest'`；
  - UUID 主键的 task/block/checkin：`client_id=主键`；
  - 非 UUID 主键：`client_id=NULL`，保留本地、本轮不推送，并在迁移报告中计数；
  - `server_version=0`；
  - `updated_at` 用现有 `created`/`start`/`completedAt`/0 回填；
  - `time_zone=NULL`，不猜测。
- `settings`/`daily_work_times` 的确定性 `client_id` 在迁移后由本地修复例程生成；
  在生成前保持 `client_id=NULL`，不进入 outbox。
- 新增 `sync_outbox`、`sync_batches`、`sync_state`、`sync_tombstones`、`sync_conflicts`、
  `sync_id_mappings`；`task_reminders`、`diaries`、`ui_preferences`、agent 表不动。
- 保留 `exportSchema=true`，提交 version 5 schema；`MIGRATION_4_5` 用
  `MigrationTestHelper` 做 v4 样本 → v5 的迁移测试；不使用 `fallbackToDestructiveMigration`。
- 不使用 `db push`/重建数据库；迁移只在 Room 内完成，服务端 schema 不在本设计内。

## 4. Push 协议

### 4.1 写入与出队

1. 所有会改变同步对象的本地写必须在**一个 Room 事务**中完成：内容表 + outbox + tombstone
   （删除时）。
2. 事务提交后由 worker 触发，不在 UI 线程发网络请求。
3. **未入批 head 的合并**（`batch_id IS NULL`，`state=pending/blocked`）：
   - 仅**没有已入批前驱**的根 create/update 可以合并或撤销；已入批前驱的 blocked 后继
     只能把新编辑合并进后继自己的 payload，不能撤销前驱或改回原批。
   - `pending create` + 后续修改：合并为最新 payload，仍为 create，`base_version=null`；
   - `pending update` + 后续修改：合并 payload，保留第一次的 `base_version`；
   - `pending create` + 删除：撤销 create，不产生服务端对象；
   - `pending update` + 删除：改为 delete，保留 `base_version`；
   - 已有 `conflict` 的对象不再自动合并新写入，进入冲突 UI（§6）。
4. **已入批意图不可变**：head 被选入批次（`batch_id` 非空且 `sync_batches` 快照存在）后，
   原行的 `object_id/op/payload_json/base_version/created_at`、批次内 mutation 顺序和
   `body_json` 全部冻结，不能合并、不能撤销、不能直接删除 outbox 行。
   - 后续编辑生成后继 `update`：`parent_op_id=原意图`、`is_head=1`、旧 head `is_head=0`、
     `state='blocked'`、`base_version=NULL`；不得把新 payload 写回原行。
   - 后续删除生成后继 `delete`：同样 blocked，`base_version=NULL`；本地内容行按 §3.4 删除/
     隐藏并写本地 tombstone，但**不产生服务端 delete**，直到原 create/update 回执到达。
   - 后继本身尚未入批，后续编辑可以合并进这个 blocked 后继；但任何后继都不得回写祖先
     已入批意图，也不能把前驱的 create 撤销。
5. **后继释放规则**：
   - 前驱回执 `applied` 或批级 `replayed`（未来兼容 `item duplicate`）：用回执的
     `server_version` 填后继 `base_version`，后继转 `pending`；回执没有版本时先做该对象的
     定向 pull，不能猜版本。
   - 前驱明确 `rejected`/服务端未接纳：`update` 后继转为 `create`（`base_version=NULL`，
     保留最新 payload）；`delete` 后继取消（服务端没有对象），本地 tombstone 保留。
   - 前驱 `conflict`：后继保持 `blocked`，进入冲突 UI；解决冲突并确定 server_version 后
     再释放后继，不自动选边。
   - 前驱状态 `unknown`（丢响应/杀进程）：后继保持 `blocked`；只重试原批次或查询/拉取，
     **不猜测原 create 未发出**，不把后继改成 create，也不因 pull 到对象而复活本地删除。
6. 合并只在同一事务内完成，避免“旧 payload 仍被 worker 取走”；同一对象的 head 唯一，
   由 `is_head` 部分唯一索引和事务共同保证。

### 4.2 批次

- 选批和快照必须在**同一个 Room 事务**中完成：生成 `batch_id`，把选中 head 的
  `batch_id`/`state=inflight` 写回，并插入 `sync_batches`（`state=prepared`、
  `created_session_id=attempt_session_id=当前sessionId`、`body_json/body_sha256`）。事务提交前
  不得发 HTTP；提交后原意图不可变（§4.1）。
- 每个批次只选**未入批、state=pending、is_head=1** 的意图；按对象/创建时间稳定排序后
  生成一次 body。`body_json` 原样保存，重试/进程恢复必须复用同一 `batch_id` 和**同一字节
  body**；不得重新读取 outbox 重新序列化，避免键顺序/空格/后继意图改变 fingerprint 后 409。
- 批次状态只用 §3.3 `sync_batches.state`：`prepared/sending/retryable/unknown/session_wait/
  recovering/applied/partial/rejected/invalid`。`retryable/unknown` 只能重发原 body；
  `session_wait` 不发 HTTP；`recovering` 仅同 owner 用户确认后短暂进入；`invalid` 不自动换 body。
- `device_id` 是安装级持久 UUID；不采集硬件序列号、MAC 或广告 ID。
- 选批上限：
  - 最多 200 项（服务端上限）；
  - 总 JSON body 控制在 200KiB 以内（按完整 JSON 的 UTF-8 字节计算，低于服务端全局 body
    限制，留出重试/网络余量）；
  - 单项 payload ≤32KiB（服务端前置校验）；超限项直接标记 `failed`，不阻塞其他项。
- body 形状严格按服务端契约：

```json
{
  "batch_id": "<uuid>",
  "device_id": "<uuid>",
  "mutations": [
    {
      "object_type": "task",
      "object_id": "<uuid>",
      "op": "update",
      "expected_version": 3,
      "payload": {"payload_version": 1}
    }
  ]
}
```

- `delete` 的 `payload` 省略或为 null；`create` 的 `expected_version=null`。
- 已入批批次的 body 以 `sync_batches.body_json` 为唯一发送源；任何重试都不得把后继意图
  或本地更新重新拼进原批。

### 4.3 结果处理

| 服务端结果 | 本地动作 |
| --- | --- |
| item `applied` | 更新内容行 `server_version`；`server_version=0` 的 create 也落新版本；outbox `done`；删除对应 tombstone 的旧版本；更新 `last_push_at`；按 §4.1 释放后继（填 `base_version`/转 pending） |
| **整批 `status=replayed`（当前服务端）** | 服务端返回原批次 items；按原 items 逐项应用（applied/conflict/rejected），不把 replayed 当新写入；成功后 outbox `done` 并释放后继；不能重造 body |
| item `duplicate`（兼容设想，当前服务端不返回） | 仅为未来兼容分支；若出现，按 `applied` 处理并先取该对象版本；当前实现不得依赖此状态 |
| item `conflict` | outbox `conflict`；保留 payload；写/更新 `sync_conflicts`；后继保持 `blocked`；触发针对性拉取（§5.4）；不自动改本地内容 |
| item `rejected` | outbox `failed`，记录 `reason`（如 `unsupported_object_type`、`payload_required`）；不做盲目重试，UI 显示需修复；若前驱 create 明确未接纳，按 §4.1 转换/取消后继 |
| 整批 `status=partial` | 按 items 逐项处理；不整批重放；批次快照保留 |
| 整批 409（同 batch 异体） | 该批 `invalid`，不自动换新 batch；outbox 行保持失败/冲突待诊断；不改本地内容；必须排查 body 变化并修复后由用户/维护流程处理 |
| HTTP 400/413/422 | 批次 `invalid`，标 `failed`，提示修复；不自动重发，不重拼 body |
| HTTP 401 | 批次保持 `(owner, attempt_session_id)`；暂停 worker，交 T31 refresh；refresh/重放仍在原 attempt；outbox/快照不丢 |
| HTTP 403 | 停止该 owner worker，清理在途状态；不重试到别的 owner |
| HTTP 429/5xx/网络超时 | 批次 `retryable`，attempts+1，计算 `next_retry_at`；outbox 保持 inflight/原 batch；不改变 payload/base_version，不换 batch_id |
| 响应丢失/进程被杀 | 批次 `unknown`；原 outbox 保留原 batch/逻辑 pending（但不恢复成可合并的裸 pending），启动后只用原 `batch_id` + 原 `body_json` 重发；不得重新选批/重拼 body，也不得猜测原 create 未发出 |

- **当前服务端语义**：同一 batch 重试返回**批级 `replayed` + 原 items**，不是逐项 `duplicate`；
  客户端按原 items 处理。`item duplicate` 只作为未来兼容设想，不能作为当前实现依赖。
- 对 `applied`/整批 `replayed` 的本地更新必须仍校验 `owner_id + attempt_session_id`；
  旧 owner/旧尝试的迟到响应直接丢弃，不能推进 cursor 或释放后继。
- `server_version` 只由 push 回执或 pull 的 `version` 更新；客户端不得自增。
- 不按客户端字符串直接改积分/VIP；这些字段不进同步 payload。
- 批次回执应用和后继释放必须在同一个 Room 事务中；成功项 done、失败项 failed/conflict，
  不能出现“内容已更新但 outbox 仍 inflight”的半状态。

### 4.4 发送前绑定 `(owner, sessionId)` 与同 owner 恢复

仅在响应应用前校验 `sessionId` 不够：普通 `ApiClient.post/get` 会读取调用时最新的
TokenStore，worker 选出 A 的 payload 后切到 B，就可能用 B 的 Bearer“合法”写入 B。
WorkManager cancel 不是发送原子保证，不能代替绑定。

1. **选批时冻结**：从 A 的 outbox 选批时读取 T31 的 `ownerId` 和
   `AccountSession.currentSessionId()`，写入 `sync_batches.created_session_id`；首次尝试的
   `attempt_session_id` 与 `created_session_id` 相同。pull 也冻结当前 `(ownerId, sessionId)`，
   只在该代次内推进 cursor。
2. **只用绑定入口**：push 使用
   `ApiClient.postAsSession(path, body, sessionId)`，pull 使用
   `ApiClient.getAsSession(path, sessionId)`（与 #29 相同的会话绑定机制）。**owner 不由 API
   参数传递**，由同步层在调用前后核对；不得用普通 `post/get` 再在响应侧“补校验”，也不得加
   额外 owner header 代替 Bearer 绑定。
3. **不匹配不发 HTTP**：发送前再次读取当前 sessionId；不等于 `attempt_session_id`，则批次置
   `session_wait`、不取 B 令牌、不发请求。A 的 outbox/快照原样保留；不能把批次改绑到 B。
4. **401 刷新/重放**：401 由 T31 refresh；若 refresh 仍保持本次 `attempt_session_id`，重放必须
   仍携带该 attempt。若 refresh/重新登录产生新代次，停止该批并保留 `session_wait`，不能静默
   用新代次发送旧 body；进入下面显式恢复流程。
5. **同 owner 显式恢复**（只允许这一条路径）：
   - 前置：批次为 `session_wait`（或恢复失败回到此态），当前认证 `userId == batch.owner_id`，
     且当前存在有效 sessionId；不同 owner 一律不可见/不可恢复，B 永远不能接手。
   - 用户确认“恢复未完成同步”后，状态置 `recovering`，把本次有效 sessionId 写入
     `attempt_session_id`；`created_session_id`、`batch_id`、`body_json`、`owner_id`、内容
     全部不变。
   - 用同一 `batch_id` + 同一 `body_json` 调 `postAsSession(path, body, attempt_session_id)`；
     服务端按 `(user_id,batch_id)` 幂等，同 owner 新会话可安全取回原批回执，**不重造 body**。
   - 回执按 §4.3 处理（当前为批级 `replayed`+原 items）；成功后释放后继。恢复请求失败可回到
     `session_wait/retryable` 再次由同 owner 确认重试，不标 `invalid`、不清 outbox。
   - 恢复取消/失败不改变原批次内容；A 下次登录 s3 仍可按同一路径再次恢复。
6. **响应后二次校验**：收到响应，在 Room 应用事务中再次核对 `ownerId` 与本次
   `attempt_session_id`；已切换则丢弃结果、不写 Room、不推进 cursor、不释放后继。服务端可能
   已经按 A 写入，但 B 不能收到 A 的 mutations，B 的 UI 也不能应用 A 的结果。
7. **B 的可见性**：切换 B 后，B 的 worker 只读取 B 的 outbox/state；A 批次处于
   `session_wait/recovering/unknown` 也不会进入 B 的选批查询，B 不能提供 A 的恢复确认。
   验收要求 B 收到 A mutations 为 0。

## 5. Pull 协议

### 5.1 基本流程

1. 从 `sync_state(owner).cursor` 开始（无记录为 0），`limit=100`（服务端会 clamp 到 1..200）。
2. 冻结该 owner 的 `(ownerId, sessionId)`，用 `ApiClient.getAsSession` 请求
   `GET /sync/pull?cursor=&limit=`；服务端按 `sync_changes.seq` 升序返回
   `changes[]`、`next_cursor`、`has_more`。
3. 一页在**一个 Room 事务**中应用；成功后才把 `cursor=next_cursor` 写入 `sync_state`。
4. 事务内再次核对 owner/sessionId；不匹配则整页丢弃，不推进 cursor。
5. `has_more=true` 继续下一 页；否则结束。
6. 不按客户端时间猜 cursor；cursor 是服务端 `seq`，不是对象 `version`。

### 5.2 变更应用（版本单调）

对每条 change，先计算该对象的 `localKnownVersion`，再做任何删除/覆盖/冲突判断：

```text
localKnownVersion = max(
  内容行.server_version（存在时）,
  tombstone.version（存在时）,
  conflict.server_version（存在时）,
  pending/blocked/inflight head 的 base_version（存在且非 null 时；create 视为 0）,
  已确认 push 回执写入的 server_version（已落到内容行/tombstone）
)
```

对一个从未见过的对象，`localKnownVersion=0`。规则：

- `change.version <= localKnownVersion`：**幂等跳过**。不降版本、不覆盖新内容、不写
  tombstone、不为旧回放新建冲突；保留 pending/blocked 后继。cursor 仍按本页 `next_cursor`
  前进（跳过旧版本不能卡住 cursor）。
- 只有 `change.version > localKnownVersion` 才允许处理：
  - `deleted=true`：本地无 pending/blocked/conflict 时，写 tombstone（version=change.version）、
    删除本地内容行、更新 known version；**旧 delete 版本不高于 known 时绝不删除**。
  - `deleted=true` 且本地有 pending/blocked/conflict：不自动删除本地；把远端删除写入冲突，
    保留本地意图；不因旧 delete 覆盖更高版本。
  - `deleted=false`：若本地有 pending/blocked/conflict，不静默覆盖 outbox；把服务端 payload
    写入 `sync_conflicts.remote_payload_json`，保持 pending/blocked/conflict，进入冲突处理；
    blocked 后继不能被 pull 直接改写或删除。
  - `deleted=false` 且本地无保护意图：按 §3.2 映射写入 Room，
    `server_version=change.version`、`updated_at=now`、owner 不变；不把 `client_id` 改写；
    应用后更新该对象 known version（内容行 `server_version`）。
- `payload_version` 不等于当前支持的 `1`：不覆盖本地，写 conflict/failed 并记录稳定错误码；
  未知字段忽略并记录字段名，字段类型非法/必填缺失则拒绝该对象。
- **页内多条**：按 `seq` 顺序遍历，但每条都要重新比较 `change.version` 与当前 known version；
  不能因为页内 seq 靠后就无条件覆盖。旧 v1 在已应用 v2 之后出现必须跳过；v2 在 v1 之后出现
  才允许应用。`seq` 只决定遍历顺序/cursor，不替代版本比较。
- **跨页/重启**：每页在一个 Room 事务中应用，只有成功才写 `cursor=next_cursor`；known version
  已持久化在内容行/tombstone/冲突中，重启后重复的旧页仍会幂等跳过，保持 v2 而不是回退。
- `payload` 为 null 的 delete：先做版本比较，再只写 tombstone，不解析 payload。

### 5.3 顺序决定

- **先 push 后 pull**：本地 outbox 代表用户明确写入；先让服务端判定版本冲突，再拉取远端
  变化。原因：如果先 pull 再 push，pull 到的新版本会让本地 pending 的 `base_version`
  立即过期，冲突面更大；先 push 能用服务端版本给出精确冲突，随后 pull 补齐远端对象。
- 但登录后的首次同步例外采用 **pull 基线 → guest 合并 → push**（§7）；否则 guest 合并
  可能把服务端已存在的对象再次 create。
- push 完成后立即 pull 一页以上，直到 `has_more=false`；不能只 push 不 pull，否则其他设备
  的变更永远看不到。

### 5.4 冲突对象的定向拉取

服务端 push 的 conflict 只返回 `server_version` 和 `reason`，**不返回当前 payload**；pull
接口也没有“按 object_id 取当前对象”的参数。因此：

1. conflict 时把 outbox 置为 `conflict`，不立即重试；后继保持 `blocked`。
2. 为该对象执行一次**定向修复拉取**：使用冻结的 `(ownerId, sessionId)` 和独立扫描游标，
   从 `cursor=0` 分页扫描到当前末尾，只挑选该 `(object_type,object_id)` 的最新 change，
   校验 `payload_version` 后写入 `sync_conflicts.remote_payload_json`。
3. 扫描结束后恢复原增量 `cursor`（不能把全量扫描的 cursor 当作增量游标，也不推进
   `sync_state.cursor`）。
4. 如果对象在服务端已不存在（只有 tombstone），remote payload 为 NULL，按“远端删除”处理。
5. 该全量扫描只用于冲突修复，不在每次普通 pull 中使用；扫描也按 §5.2 版本单调比较，
   旧版本不覆盖已有最新值；规模变大时需要服务端提供
   `GET /sync/objects/{object_type}/{object_id}` 或 push conflict 直接带 payload（§13）。
6. 扫描过程同样受 §4.4 会话绑定和响应后二次校验约束；代次不匹配则整页丢弃。

## 6. 冲突规则

### 6.1 权威边界

服务端权威的只有：**归属用户、对象类型/UUID、当前版本、删除 tombstone、批次幂等和
RLS/事务**。服务端**不校验** payload 内部字段，因此不能声称“服务端保证 locked/done”。

客户端对以下字段采用保守的“受保护字段”策略：

- `task.done`、`block.locked`、`block.done`、`checkin`、`availability` 的日期/时区、
  `settings` 的作息时间：不允许静默 LWW 覆盖；
- `points`、`VIP`、钱包：**不在同步白名单**，只通过账户 API 读取，客户端不能写入；
- 删除：不自动复活，不自动覆盖本地未推送编辑。

### 6.2 按对象规则

| 对象 | 可自动合并的字段 | 必须人工确认的字段 | 规则 |
| --- | --- | --- | --- |
| `task` | 无（整对象版本冲突） | 标题/备注/截止/工时/分类/重要性/完成 | 版本不一致 → conflict；文本字段可在 UI 逐字段选择“本地/远端”，结构字段必须整对象选择；`done` 不自动改 |
| `block` | 无 | start/end、locked、done | 时间变更不自动合并；`locked/done` 不一致必须提示，不能自动解锁/改完成 |
| `checkin` | 相同 payload 的重复 create | 同 ID 不同 payload | 追加型；同 ID 同 payload 视为已应用；不同 payload 为 conflict，不覆盖、不删除旧 checkin |
| `availability` | 无 | date/start/end/time_zone | 时区/日期不一致即冲突；不把 A 时区的可用时间静默应用到 B |
| `settings` | 无 | start/end、time_zone | 整对象冲突；不自动跨时区改写作息 |

### 6.3 删除 vs 修改

- 远端 `deleted` 且本地无 pending：**删除优先**，本地删除并写 tombstone。
- 远端 `deleted` 且本地有 pending/blocked/conflict：**不删除本地**；进入冲突，显示“远端已删除”。
  UI 选择：
  1. 放弃本地修改；
  2. 保留为新对象（生成新 UUID，重新 create；旧 ID 仍为 tombstone）；
  3. 取消，稍后处理。
- 本地删除且远端随后修改：本地 delete 先按版本 push；若服务端返回 conflict，保留本地
  tombstone 意图并进入冲突；不能因为远端修改而自动复活本地内容。
- 已入批 create/update 的本地删除不能改写原行：按 §3.4 生成 `blocked` 后继 delete，等
  前驱回执确定 `base_version` 后再发；前驱 `unknown` 时不得猜“未发出”而取消。
- 旧离线副本的 create/update 如果版本 ≤ tombstone.version，直接丢弃，不复活。

### 6.4 时区/日期边界

- 瞬时（deadline、block start/end、checkin completed_at）统一 epoch millis，传输不随设备时区改变。
- 业务日/可用时间使用 `YYYY-MM-DD` + `start_minute/end_minute` + IANA `time_zone`；
  `end_minute=1440` 表示当天结束，是合法值；不做静默 DST 修正；无效本地时刻拒绝并让用户选择。
- `settings` 的 start/end 是本地墙钟；`time_zone` 不同即冲突，不自动换算。
- 服务端业务日规则（`BUSINESS_TIMEZONE`）只用于签到等业务，不用于改写客户端本地日程。

### 6.5 冲突 UI

- 冲突列表按 owner 展示对象类型/标题/本地修改时间/远端版本/原因。
- 单对象详情：左右对比本地与远端 payload；文本字段可逐字段选择，结构字段整对象选择。
- 批量操作只允许“全部保留本地为新建”/“全部接受远端”，并二次确认；不能默认丢弃。
- 未解决冲突的对象不再进入 outbox 自动重试；用户解决后写新 outbox（或标记 done）。
- 解决事务必须同时更新内容行、`server_version`、outbox/conflict 状态，失败整体回滚。

## 7. 访客 → 账户合并

### 7.1 触发与前提

- 只在**登录成功或已有会话 restore 成功**、且 `AccountSession.begin(accountSession)` 成功后触发。
- 先完成账户 **pull 基线**（cursor=0 到末尾，或已有 cursor 的增量）；pull 失败则不合并。
- 显示访客任务/安排/签到/可用时间数量；用户确认后才执行。注册不自动登录，不触发合并。
- 访客与账户的 `owner_id` 分别为 `guest` 和认证用户 UUID。

### 7.2 按对象类型决定目标 ID

guest 合并在一个 Room 事务中完成，但两类对象的 ID 规则不同；不能再用“保留 client_id/
object_id”一条规则覆盖 settings/availability。

#### 可保留 UUID：`task`、`block`、`checkin`

- 把 `owner_id` 从 `guest` 改为账户 userId；`id/client_id/object_id` 保持不变。
- 同事务把该对象未入批的 guest outbox 头意图改成账户 owner；`server_version` 仍为 0 的
  create 继续保持 `base_version=NULL`；已有 `server_version` 的对象若需要上传，按 update 处理。
- 若账户基线已有相同 object_id：比较 payload；完全一致则跳过并标记已合并；不一致则
  进入冲突 UI，不重复 create，也不覆盖 A。
- 任务被移动时，其 blocks/checkins 一并移动；子对象冲突时按 §6.5 处理，不静默丢子对象。
- 这些对象不需要 guest→account ID 映射，因为 object_id 原样保留。

#### 自然键对象：`settings`、`availability`

guest 派生 ID 只在本机有效，**不保留、不发送**。目标 ID 按账户 owner 的 canonical UUIDv5：

- `settings`：`UUIDv5(WHALETODO_SYNC_NAMESPACE, "settings:" + accountOwnerId)`；
- `availability`：`UUIDv5(WHALETODO_SYNC_NAMESPACE, "availability:" + accountOwnerId + ":" + date)`。

处理规则：

- 若账户 A 没有该自然键对象：用 canonical ID 创建账户内容行，并写 `outbox create`
  （`base_version=NULL`, `server_version=0`）；不使用 guest ID。
- 若账户 A 已有 canonical 对象：不创建第二个；把 guest 字段按 §7.3 与 A 合并/冲突，
  outbox 改为针对 canonical ID 的 update（`base_version=A.server_version`），不发送 guest ID。
- 若 A 的 canonical ID 已有 tombstone：**不复活**；把 guest 内容写入冲突清单，由用户选择
  “恢复/保留删除/另建新对象”，不能静默重建 canonical 对象。
- 同事务写 `sync_id_mappings`（guest_object_id→account_object_id）和 guest tombstone
  （`owner_id='guest'`, version=0）；删除 guest 内容行；账户内容行成为唯一副本。
- 如果 guest 内容行本身是删除意图：不要在 A 上删除同名 natural key；只记录映射/guest
  tombstone，A 的对象保持原样，避免把 guest 的删除扩大成账户删除。
- guest 已 tombstone 的对象（task/block/checkin 或自然键）不进入合并，不生成 create；
  guest 的 delete 意图也不能转换成 A 的 delete。只保留 guest tombstone/映射，保证合并后
  不复活，也不会误删 A 已有对象。

`task_reminders`、`diaries` 随 owner 移动（本地-only，不写 outbox）；`ui_preferences` 的
`device` 行不移动。移动后 guest 工作区为空；退出后通过重新登录账户访问，不在 guest 继续
保留。拒绝合并/取消确认时 guest 数据保持原样，不删除任何本地数据。

### 7.3 A 已有自然键的字段合并

A 已有 canonical settings/availability 时，以 A 为基线，按字段比较，不用 guest 整对象覆盖：

| 对象 | 可自动补齐的字段 | 必须人工确认的字段 | expected_version |
| --- | --- | --- | --- |
| `settings` | A 为 NULL 且 guest 有值的 `start_hour/end_hour/time_zone` | 两边都有值且不同 | A 的 `server_version` |
| `availability` | A 为 NULL 且 guest 有值的 `start_minute/end_minute/time_zone` | start/end/time_zone 任一不同；`end_minute=1440` 合法 | A 的 `server_version` |

- 字段完全相同：不写 outbox，不产生版本变化，只记录已合并。
- 只存在 A 的空字段可补齐：写 `outbox update`，payload 为合并后的完整对象，
  `base_version=A.server_version`，`expected_version` 一致。
- 两边字段不同：不自动选边；把 guest payload、A 的 current payload/version 写入
  `sync_conflicts`，标记 `reason=natural_key_conflict`，用户选择后再写 update（仍带
  `base_version=A.server_version`）。不能静默覆盖 A 的作息/可用时间。
- 用户选择后若 A 已被其他设备更新，`expected_version` 不匹配 → 重新进入 conflict；
  不允许把旧版本直接重试。
- B 设备后续 pull 到同一 canonical ID；因为 ID 由 `(A,自然键)` 确定性生成，B 不应再创建
  第二个同日 availability/设置对象。B 本地若已有同一 canonical ID，按普通 pull 版本规则处理。

### 7.4 guest outbox 重写

- 合并前 guest outbox 必须没有 `batch_id`（guest 没有绑定会话，不应产生批次）；若发现非空
  `batch_id`，中止合并并报诊断，不重写已入批意图。
- 同一自然键只保留一个 head（合并未入批的 guest 意图）；task/block/checkin 只改 owner，
  object_id 不变；settings/availability 把 `object_id` 改成 canonical ID。
- 账户 A 已有对象：create 改为 update（`base_version=A.server_version`）；账户 A 没有对象：
  保持 create（`base_version=NULL`）；账户 A 已有相同字段：不写 outbox，直接 done。
- 账户 A 有 canonical tombstone：不产生 create/update，写冲突/恢复选项；绝不能复用
  tombstone ID 重新 create。
- 重写必须保留原 `op_id`（用于本地幂等）和 `parent_op_id` 链；不得改写已完成/冲突意图。
- 合并事务同时写内容行、`sync_id_mappings`、guest tombstone、outbox 重写；任一步失败
  整体回滚，guest/account 都不变，outbox 不残留半成品 create。

### 7.5 事务与失败

- 合并是一个 Room 事务：pull 基线已完成 → 用户确认 → 内容迁移/字段合并 → outbox 重写 →
  mapping/tombstone → 提交；提交后才启动账户 worker。
- 失败：整体回滚，guest/account 都不变，显示可重试错误；不显示 payload 正文。
- 部分 natural-key 冲突：冲突 payload 存本地 `sync_conflicts`，用户解决前不写账户内容/outbox；
  guest 行可按“已接管/冲突”状态隐藏，不能静默丢用户数据。
- 合并成功后 worker 只处理账户 owner；guest worker 不再存在。

### 7.6 UI

- 合并确认页：数量、最近修改时间、预计上传条数、自然键冲突数；按钮“合并 / 稍后 / 取消”。
- 完成后 toast/列表显示成功数、冲突数；失败显示可重试错误，不显示 payload 正文。
- natural-key 冲突项进入 §6.5 的统一冲突页面，显示 A 当前版本与 guest 字段，不默认选边。

## 8. 账户隔离与缓存

### 8.1 分区键

- 所有同步内容、outbox、batch 快照、state、tombstone、conflict、id mapping 均以
  `owner_id` 为第一分区键：`guest` 或服务端 userId。
- 所有 DAO 查询/更新必须带 `owner`；不允许无 owner 的 `SELECT * FROM tasks` 参与同步，
  也不允许跨 owner 的 block/checkin 外键。
- `settings`/`daily_work_times` 的复合主键包含 owner；任务/块/签到也使用 `(owner_id,id)`。
- `sync_state.device_id` 是安装级值，但 cursor/worker 按 owner 独立。

### 8.2 登录/换号/退出与发送绑定

- 登录成功：`AccountSession.begin` + 账户基线 pull + 访客合并（可选）+ 启动该 owner worker；
  worker 启动时读取并冻结当前 `(ownerId, sessionId)`。
- 换号/退出：立即取消旧 owner 的 WorkManager unique work；把 in-flight 批次的响应标记为
  不可应用；快照/outbox 保留并置 `session_wait/unknown`（不能改绑到 B）；清空当前 UI 的
  内存快照；旧 owner 的 outbox/cursor 保留但不运行。
- **发送前绑定**：push/pull 都使用 §4.4 的 `postAsSession(path, body, sessionId)` /
  `getAsSession(path, sessionId)`；push 以 `attempt_session_id` 发送，pull 冻结当前
  `(ownerId, sessionId)`。凭据代次不匹配时不发 HTTP，不读取 B 的 TokenStore。不能只用
  “响应应用前校验”，也不能用 owner header 代替 Bearer 绑定。
- 401：T31 refresh 后若仍在本次 `attempt_session_id`，在原 attempt 重放；refresh 产生新代次
  则批次保持 `session_wait`，不能静默换 B 发送。
- 同 owner 重新登录：只有当前认证 userId == batch.owner_id 且用户确认“恢复未完成同步”后，
  才允许 `session_wait → recovering`，把新 sessionId 写入 `attempt_session_id`；batch/body/
  owner/created_session_id 不变。不同 owner（尤其 B）不能恢复、不能重绑，B 的请求数为 0。
- 恢复失败/取消：回到 `session_wait/retryable`，可再次同 owner 重试；不标 invalid、不重造 body、
  不删除 outbox/后继。A 下次登录 s3 仍可继续同一恢复路径。
- WorkManager cancel 只停止后续调度，不是发送原子保证；批次快照和绑定入口共同保证
  不把 A 的 mutations 发到 B。
- 捕获 T31 的 `sessionId` 与 owner：push 在应用事务前核对 `owner` 与本次
  `attempt_session_id`，pull 核对当前 `(ownerId, sessionId)`；不等则丢弃，不写 Room、
  不推进 cursor、不释放后继。
- 同步层不保存 token、不拼 owner header；token refresh 仍由 T31 的 ApiClient 负责。

### 8.3 缓存清理

- **默认不删除**旧 owner 的本地数据：按 owner 保留，UI 不展示，只有同一 owner 重新登录可见。
  这样离线编辑/未解决 outbox 不会因退出而丢失。
- 提供“清除此账户本地数据”显式操作：删除该 owner 的内容/outbox/batch 快照/state/
  tombstones/conflicts/id mappings，保留 guest；需二次确认并提示未同步数据会丢失。
- 清除 token 不清 guest 数据，也不删除账户缓存；guest 清理只能由用户独立操作。
- `agent`/`diaries`/`reminders` 同样按 owner 隔离；diaries/reminders 本轮不参与同步。
- Room 本身不是加密数据库；本文不声称静态加密，只要求应用沙箱 + owner 过滤；如需更强保护另立加密方案。

## 9. 离线、重试与调度

### 决定

- 使用 **WorkManager**（Android Jetpack）做后台同步；v1 不引入前台服务。
- unique work name：`sync-<owner_id>`；同一 owner 串行，不同 owner 不并行。
- 约束：`NetworkType.CONNECTED`；不做“仅 WiFi”默认，演示环境可能用热点。
- 触发：
  1. 本地写事务后 debounce 1s 请求一次同步（不是每个字段都发）；
  2. App 启动/回到前台；
  3. 网络恢复；
  4. 周期任务每 15 分钟（WorkManager 最小周期），只在有 pending 时实际发请求；
  5. 冲突页/同步页手动重试。
- 退避：30s × 2^attempts，上限 6h，加 ±20% 抖动；`next_retry_at` 持久化。
- 429 优先按服务端 `Retry-After`（若有）覆盖退避；没有则按上式计算。
- 进程被杀：
  - `sync_batches` 快照与 outbox `batch_id` 持久化；
  - 启动时把 `sending` 超过租约（例如 5 分钟）的批次标 `unknown`；**不恢复 pending、不重选批、
    不重拼 body**，只用原 `batch_id` + 原 `body_json` 重发；
  - 若服务端已处理，同 batch_id 返回**批级 replayed + 原 items**，客户端按 items 落 done，
    再释放后继；
  - 当前 owner/sessionId 与 `attempt_session_id` 不匹配时置 `session_wait`，不换 B 令牌发送；
    同 owner 重新登录后必须由用户确认显式恢复，才写新 `attempt_session_id` 并重发同一 body；
  - 进程在 `recovering` 中被杀：若当前 session 仍等于 `attempt_session_id`，重启继续 sending；
    否则回 `session_wait`，再次由同 owner 显式恢复；不重造 body；
  - 不因进程重启清空 pending/conflict/unknown 或已入批意图。
- 飞行模式：worker 保持 pending；网络恢复后再计时；不把 inflight 批次误判为失败。
- 手动重试：只重置 `next_retry_at=0`；不重写已入批 body，conflict/failed 由用户解决。
- 本地写失败（Room 事务失败）：不产生 outbox；UI 报错，保持原数据。

## 10. 错误与可观测性

| 情况 | 客户端行为 | 是否自动重试 |
| --- | --- | --- |
| 401 UNAUTHENTICATED / 会话切换 | 暂停该 owner worker；T31 refresh/重放必须留在本次 `attempt_session_id`；不匹配则 `session_wait`，outbox/快照保留 | 否，等同 owner 恢复或重新登录 |
| 403 FORBIDDEN（owner 不符） | 停止 worker，清 in-flight；不向其他 owner 重发 | 否 |
| 400/413/422（payload/格式/超限） | 批次 `invalid`；显示可操作错误；不自动重发/不重拼 body | 否 |
| 409（同 batch 异体） | 批次 `invalid`；保留快照供诊断；不自动新造批次 | 否 |
| 429 RATE_LIMITED | `retryable`；同一 body 退避重试 | 是 |
| 5xx/UPSTREAM_UNAVAILABLE | `retryable`；同一 body 退避 | 是 |
| 网络不可达/超时 | 批次 `retryable`；同一 body 退避；不错误地标 conflict | 是 |
| 服务端 item conflict | 转 conflict + 定向 pull；不自动改内容；后继保持 blocked | 否，等用户 |
| 响应无法解析/未知状态 | 批次 `unknown`；保留快照/outbox；不猜测成功，重发原 body | 是（保守退避） |

日志与指标：

- 只记录 `owner` 的散列/短标识、`op_id`、`object_type`、`op`、`result`、HTTP 状态、
  `request_id`（若响应有）、耗时、attempts；**不记录 prompt/response/payload 正文、
  token、验证码、日记内容、备注、邮箱**。
- 指标：pending 数、conflict 数、failed 数、最老 pending 年龄、最近 push/pull 时间、
  429/5xx 计数；不把指标标签做成高基数（不把 object_id 当标签）。
- 用户可见状态：同步中/已同步/有待处理冲突/失败；失败页提供重试与详情（不含正文）。

## 11. 迁移与回滚

### 迁移步骤（设计）

1. 生成并提交 version 5 Room schema；评审字段/索引/主键。
2. 编写 `MIGRATION_4_5`：建新表、复制、校验行数与引用、drop 旧表、rename；单事务。
3. 迁移后修复例程：为 `settings`/`daily_work_times` 生成确定性 `client_id`；
   统计非 UUID 主键的 task/block/checkin，标记 local-only。
4. 首次启动只读校验：owner 列非空、复合主键、`server_version>=0`、tombstone 无重复、
   outbox 每对象一个 head、`sync_batches` 有 owner/created_session_id/attempt_session_id/
   body/body_sha256；失败进入“只读/修复”状态，不自动删除用户数据。
5. 迁移测试：v4 样本库（有任务/块/签到/设置/可用时间、无同步列）→ v5；断言数据、主键、
   索引、owner=guest、client_id/server_version 回填；`MigrationTestHelper` 跑通。
6. 不使用 destructive migration；不在迁移中清空 outbox（v4 没有 outbox）。

### 回滚

- Room 不自动降级；v5 打开失败时保留数据库文件，进入只读/诊断，不执行 `fallbackToDestructiveMigration`。
- 迁移失败：事务回滚，旧表保留；提供“导出诊断/重试迁移”，不自动清库。
- 发布回滚只回滚 App 版本时，v5 数据不能被旧 v4 读取；需保留升级前备份/由用户选择清除本地数据。
- 清 outbox 的条件：用户显式“清除此账户本地数据”，或 outbox 行已确认损坏且用户确认；
  不以“登录失败/换号”自动清空。
- 服务端迁移/回滚不在本设计范围。

### 单元（JVM）

| 测试 | 通过标准 |
| --- | --- |
| 未入批 outbox 合并/撤销 | `batch_id=NULL` 时 create/update 合并、create+delete 撤销、update+delete 改 delete；base_version 正确；payload 不丢字段 |

| 后继释放 | 前驱 applied/批级 replayed 后填版本并转 pending；前驱 rejected 时 update 转 create、delete 取消；前驱 conflict/unknown 时保持 blocked，不猜测 create 未发出；item duplicate 仅兼容分支 |
| 批次选择/上限 | 快照与 outbox batch_id 同事务；≤200 项、总 body ≤200KiB、单项 ≤32KiB；超限单项 failed 不阻塞；batch_id/body_sha256 稳定 |
| 冲突比较 | 版本不一致不自动覆盖；受保护字段不自动选边；删除 vs 编辑按 §6.3 |
| 保留 UUID 合并 | task/block/checkin 移动 owner 后 object_id/client_id 不变；A 已有同 ID 同 payload 跳过、不同 payload 冲突 |
| 自然键 canonical ID | settings/availability 使用固定 UUIDv5 测试向量；guest ID 不保留；A 无对象 create、A 有对象 update/字段合并、A tombstone 不复活 |
| guest outbox 重写 | 未入批 guest 意图的 object_id 改 canonical、owner 改 A；A 已有对象时 base_version=A.server_version；写 mapping/guest tombstone；失败全回滚 |
| tombstone | 版本 ≤ tombstone 的旧 change 被丢弃；更高版本可恢复；guest tombstone 不会被 A 的 create 覆盖 |
| pull 单调版本 | 以内容行/tombstone/conflict/pending base/已确认回执的 max 为 known；`change.version<=known` 跳过；旧 delete 不删更高版本；跳过不阻塞 cursor |
| payload 版本/未知字段 | 未知 `payload_version` 不覆盖；未知字段忽略并记录字段名；非法/必填缺失拒绝；`end_minute=1440` 合法 |
| 时区/日期 | epoch 不变；availability/settings 不同 time_zone 判冲突；`end_minute=1440` 合法；DST 无效时刻拒绝 |

### 集成（fake server）

| 测试 | 通过标准 |
| --- | --- |
| push applied | server_version 更新、outbox done、local content 一致；随后后继 intent 被正确释放 |
| 批级 replayed+原 items | 同 batch/body 重试返回 `replayed` 和原 items；按 items 落 done/conflict/rejected；不重复创建；不依赖 item duplicate |
| push partial/rejected | 按 item 处理；成功项 done，失败项 failed/conflict，不整批重放 |
| batch 幂等/不可变 | 同 batch 同 body 重试成功；body 任一字节变化返回 409；客户端不自动换 batch 重拼 |
| batch 409 | 批次 `invalid`；本地不写 server_version；快照保留；不自动新 batch |
| 发送前会话绑定 | 选批 A 后切 B：不取 B 令牌、不发 HTTP，B 收到 A mutations=0；A 的 outbox/快照保留 |
| 同 owner 恢复 | A s1 批 unknown→退出→A s2 登录：确认 userId==owner 且用户确认→recovering→sending；created_session_id 保留、attempt_session_id=s2；原 batch/body replay；后继释放 |
| 不同 owner 恢复拒绝 | A 批次 session_wait 时 B 登录：B 不可见/不能确认恢复、请求数 0；A batch 不被改绑 |
| 恢复失败重试 | 同 owner 恢复请求失败回 session_wait/retryable；可再次恢复；不 invalid、不重造 body/outbox |
| 401 同 attempt | refresh/重放仍带本次 `attempt_session_id`；代次变化置 `session_wait`，随后只允许同 owner 显式恢复 |
| 响应后切换 | 响应回包前切 B，Room 应用事务拒绝；不推进 cursor/不释放 A 后继 |
| 进程被杀/丢响应 | 批次 `unknown`，重启用原 batch_id+原 body 重发；不重建 body；同 batch 返回批级 replayed+原 items 后落 done |
| pull 分页 | cursor 按 next_cursor 前进；has_more 循环；不跳页/不丢页；session 不匹配整页丢弃 |

| pull 旧 delete | 本地 known ≥ 旧 delete.version：不删除/不回退；更高版本 delete 才删并写 tombstone |

| 401/429/5xx | 401 绑定/暂停；429/5xx 同 batch 退避；outbox/快照保留 |
| 冲突修复 pull | 独立扫描游标从 0 扫描；保留原增量 cursor；取最新版本；不误应用其他对象；旧版本同样跳过 |
| A 已有自然键 | A 已有同日 availability/settings：identical 不写；可补齐字段写 update；不同字段进 conflict，带 expected_version |

## 13. 服务端边界答复（2026-10-27，依据当前代码）

以下为设计采用的边界，不是“已部署/已验证”的承诺；实现前若服务端代码变化，需重新核对。

1. **cursor/tombstone 保留**：当前服务端不清理 `sync_changes`/tombstone，也没有 cursor 过期/
   重置协议。客户端先按“历史保留”实现，不承诺永久；未来若压缩历史，必须先定义基线/重置
   协议，不能让旧 cursor 在历史被删后继续成功。
2. **冲突 payload**：push conflict 不带当前 payload。v1 使用**独立扫描游标**从 `cursor=0`
   分页扫描，保留原增量游标，取该对象最新版本；不新增服务端接口，也不把全量扫描游标当增量。
3. **payload 版本/未知字段**：定义 `payload_version`（当前 1）。未知版本不覆盖本地，进入
   conflict/failed；未知字段忽略并记录字段名（不含值），类型非法/必填缺失拒绝该对象。
   settings 本轮只映射作息；availability `end_minute` 允许 1440，不能统一限制为 0..1439。
4. **reminders/diaries/agent 历史**：本轮本地-only；不扩服务端白名单、不扩 schema、不做
   隐私范围变更。后续入白名单须单独立项评审。
5. **限额**：单批 ≤200 项、完整 JSON ≤200KiB（UTF-8 字节）、单 payload ≤32KiB；`Retry-After`
   有则尊重，否则按 30s..6h 退避；200 项/200KiB 是客户端预算，不等于生产反代边界已验证。
6. **时区**：客户端显式传 IANA `time_zone` 与墙钟/瞬时字段；服务端不改写个人日程，
   `BUSINESS_TIMEZONE` 不用于转换这些 payload；客户端处理 DST 无效/重复时刻。
7. **tombstone**：保留，不因 cursor 前进删除；删除协议与全量基线未来一起评审；v1 不把
   tombstone 当可清理缓存。

以上 7 条与 §3–§9 的本地模型/协议一致；本轮只改设计文档，未实现同步客户端、未迁库、
未清理任何用户数据或部署服务端变更。
