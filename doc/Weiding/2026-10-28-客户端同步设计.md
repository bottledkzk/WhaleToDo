## 1. 目标与非目标

### 目标

1. 多设备可用：同一账户在 A/B 设备上都能读到同一份任务、安排、签到、可用时间与设置。
2. 离线可用：本地写入不等待网络；断网/进程被杀后 outbox 仍可恢复并幂等重试。
3. 冲突可见：版本冲突不静默覆盖用户输入；服务端当前值和本地待推送值都可展示、可选择。
4. 访客数据可合并：访客记录在用户明确确认后归入账户，不重复创建。
5. 账户隔离：所有同步读写、缓存、worker、游标和 outbox 都按 owner 分区；A 的迟到结果不能写入 B。
6. 幂等不重复：批次、对象创建、删除和 checkin 重复提交不产生重复记录或重复通知。

### 非目标

- 实时协作、多人同时编辑同一对象的 OT/CRDT。
- 服务端全文搜索、跨账户共享、公开链接。
- AI 会话/消息/日记正文的云端同步（本轮；见 §2 的边界决定）。
- 服务端 schema、RLS、迁移或部署变更；这些属于数据库负责人的独立 PR。
- 客户端通知的云端重放；提醒仍由本地最终状态驱动。

## 2. 现状与缺口

### 服务端已有能力

| 能力 | 现状 | 客户端影响 |
| --- | --- | --- |
| `POST /sync/push` | Bearer 登录；`batch_id` UUID、`device_id` ≤64；单批 1..200 项；每项 payload 前置上限 32KiB | 批次必须可重放，body 不可在重试时改变 |
| 对象类型 | `task`、`block`、`checkin`、`availability`、`settings` | 只有这五类可作为服务端对象 |
| 操作 | `create`、`update`、`delete` | 新建 `expected_version=null`；更新/删除必须带当前服务端版本 |
| 版本 | `sync_changes` 按对象追加 `version`；`decideMutation` 对版本不一致返回 `conflict` | 客户端必须保存每对象 `server_version`，不能只存“已同步”布尔 |
| 幂等 | `sync_batches(user_id,batch_id)` 唯一；同 batch 同内容返回原回执，异体 409；`sync_mutations` 记录结果 | 同一批重试必须复用同一个 `batch_id` 和同一 body |
| 结果 | 整批 `applied|partial|rejected`；逐项 `applied|conflict|rejected` | 按 item 更新 outbox，不能整批重放 |
| 拉取 | `GET /sync/pull?cursor=&limit=`；按 `seq` 升序；`next_cursor`、`has_more` | 游标是服务端变更序列，不是对象版本 |
| 删除 | `sync_changes.deleted=true` | 客户端需要 tombstone 防止旧副本复活 |
| 安全 | 内容表 RLS + 事务内 `set_config('app.user_id')`；批次串行化 | 客户端不得提交 owner/user_id；服务端从 Bearer 取身份 |

已确认的边界：服务端**不解释** payload 内部业务字段。`sync_changes` 保存客户端的 JSON，
服务端只校验对象类型、UUID、操作、版本、大小和事务/RLS。因此本文的 payload 字段是
**客户端提议的契约**；服务端当前按 opaque JSON 存储，不校验这些内部字段。

### 客户端现状

- Room 版本 4，已有 `tasks`、`blocks`、`checkins`、`settings`、`daily_work_times`，
  以及按 owner 分区的 `task_reminders`、`diaries`、`ui_preferences`、agent 表。
- `tasks`/`blocks`/`checkins`/`settings`/`daily_work_times` **没有 owner_id**；
  目前是单工作区模型，不能直接承担多账户隔离。
- 没有 outbox、没有服务端版本列、没有 cursor、没有 tombstone、没有冲突表。
- `DeskRepository` 的写入直接落 Room；没有“本地事务 + outbox”边界。
- T31 已引入 `AccountSession.sessionId`、`currentSessionId()` 和代次 guard；
  同步必须复用，而不是另建账户代次。

### 缺口决定

| 缺口 | 决定 | 理由 |
| --- | --- | --- |
| `task_reminders` | **本轮不同步，本地-only** | 服务端白名单没有该类型；通知是设备本地 AlarmManager 行为，跨设备同步会产生重复通知；T26 已按 owner 本地隔离 |
| `diaries` | **本轮不同步，本地-only** | 服务端白名单没有该类型；日记正文隐私等级更高，需要单独的数据最小化/加密评审；AI 日记不是同步对象 |
| `ui_preferences` | **本轮不同步，本地-only** | 主题、设备时区、星期偏好是设备/本地 UA 偏好；本轮 settings 只映射 `SettingRow` 的作息设置，避免把设备偏好混入账户设置 |
| agent 会话/消息 | **本轮不同步** | 与 AI 历史同步无关，且包含提示词/答复正文；另立隐私与保留期设计 |
| 未来 reminders/diaries 入白名单 | **另开服务端 PR**：新增白名单、RLS 字段、payload 约束、冲突规则和隐私评审后再进同步 | 不在客户端设计里偷跑服务端字段；不能把本地表直接当已支持 |

所以本设计的同步白名单严格为：
`task`、`block`、`checkin`、`availability`、`settings`。其余数据留在本地，后续单独设计。

## 3. 对象映射与本地数据模型

### 3.1 通用规则

- `object_type` 使用服务端枚举；`object_id` 必须是 UUID（服务端强制）。
- 客户端不发送 `owner_id`/`user_id`；owner 只存在本地授权上下文和服务端 Bearer 中。
- `payload` 为客户端 JSON；服务端按 opaque JSON 存储，不校验字段。字段名一次冻结后，
  客户端升级必须兼容旧 payload。
- 所有瞬时时间使用 **epoch millis（UTC）**；业务日期使用 `YYYY-MM-DD` 字符串；
  本地墙钟时间使用分钟或小时整数，并附 IANA `time_zone`。
- 每对象本地新增：
  - `owner_id TEXT NOT NULL`：`guest` 或账户 userId；
  - `client_id TEXT`：稳定客户端 UUID；为空表示本轮不具备同步资格（例如旧非 UUID 主键）；
  - `server_version INTEGER NOT NULL DEFAULT 0`：0 表示尚未在服务端建立；
  - `updated_at INTEGER NOT NULL`：本地最后修改毫秒；只用于 UI/排序，不作为冲突胜负依据。
- 不使用对象级 `deleted` 布尔列；删除用 `sync_tombstones` 表达（§3.4）。

### 3.2 五类对象的 Room 映射

#### `task`

| 本地列/来源 | payload 字段 | 说明 |
| --- | --- | --- |
| `id` | 不放入 payload | 作为 `object_id`；必须 UUID |
| `title` | `title` | 去首尾空格；非空；长度按现 UI 约束 |
| `minutes` | `minutes` | 分钟；0..525600 |
| `deadline` | `deadline` | epoch millis；**0 表示无截止** |
| `importance` | `importance` | 1..5 |
| `done` | `done` | 布尔；受保护字段 |
| `created` | `created` | epoch millis |
| `note` | `note` | 文本；可空字符串 |
| `chunkMinutes` | `chunk_minutes` | 分钟 |
| `splittable` | `splittable` | 布尔 |
| `category` | `category` | `none/study/exercise/entertainment/work/social/travel/rest` |

- `locked` 不在 task；锁定属于 block。
- 新任务 `id` 生成 UUID；旧数据若主键不是 UUID，`client_id=null`，保留本地但不推送，
  升级报告列出数量，待修复后再参与同步。

#### `block`

| 本地列 | payload | 说明 |
| --- | --- | --- |
| `id` | 不放入 payload | `object_id` |
| `taskId` | `task_id` | 必须同 owner 的任务 |
| `start`/`end` | `start`/`end` | epoch millis；`end > start` |
| `locked` | `locked` | 手动锁定；受保护字段 |
| `done` | `done` | 受保护字段 |

- 一个 block 对应一个对象；自动排程生成的 block 与手动 block 使用同一对象类型。
- 修改 block 必须保留时长约束；与 `locked/done` 的冲突不自动覆盖。

#### `checkin`

| 本地列 | payload | 说明 |
| --- | --- | --- |
| `id` | 不放入 payload | `object_id` |
| `taskId` | `task_id` | 同 owner 任务 |
| `completedAt` | `completed_at` | epoch millis |
| `rating` | `rating` | 1..5 |

- checkin 是**追加型**对象：只 create，不 update/delete。
- 同 `object_id` 已存在且 payload 相同 → 视为已应用；payload 不同 → conflict，不覆盖。

#### `availability`

| 本地列 | payload | 说明 |
| --- | --- | --- |
| `date` | `date` | 本地业务日 `YYYY-MM-DD` |
| `startMinute`/`endMinute` | `start_minute`/`end_minute` | 0..1439，`end > start` |
| `timeZone`（新增） | `time_zone` | IANA；迁移后为 NULL 的行在用户首次修改时补当前 zone |
| `clientId`（新增） | 不放入 payload | 由 owner + date 确定性生成 UUIDv5；`object_id` 使用它 |

- `availability` 的自然键是 `(owner_id,date)`；服务端对象 ID 使用确定性 UUIDv5，
  避免“date 不是 UUID”而无法 push。
- 不同时区的同一日期不可自动合并；payload/本地行的 `time_zone` 不同即视为冲突候选。

#### `settings`

| 本地列 | payload | 说明 |
| --- | --- | --- |
| `id`（固定 1） | 不放入 payload | 每 owner 一个 settings 对象 |
| `startHour`/`endHour` | `start_hour`/`end_hour` | 本地墙钟小时；`0 <= start < end <= 24` |
| `timeZone`（新增） | `time_zone` | IANA；NULL 时本轮不自动推送，避免猜测 |
| `clientId`（新增） | 不放入 payload | 由 owner + `"settings"` 确定性生成 UUIDv5 |

- `settings` 只映射 `SettingRow` 的作息设置，不包含 `ui_preferences` 的主题/设备时区/星期偏好；
  后者本轮本地-only（§2）。
- 当 `time_zone` 为 NULL 时，本地仍可用，但该 settings 不进入 outbox，直到用户显式选择/修改
  时区（避免 A 设备用 Asia/Shanghai、B 设备用 Europe/Berlin 静默覆盖）。

### 3.3 本地同步结构（设计，不在本任务建表）

#### `sync_outbox`

| 列 | 类型/约束 | 说明 |
| --- | --- | --- |
| `op_id` | TEXT PK | 每次本地变更的 UUID |
| `owner_id` | TEXT NOT NULL | `guest` 或账户 userId |
| `object_type` | TEXT NOT NULL | 五类白名单 |
| `object_id` | TEXT NOT NULL | 服务端 UUID |
| `op` | TEXT NOT NULL | `create/update/delete` |
| `payload_json` | TEXT | create/update 的规范化 JSON；delete 为 NULL |
| `base_version` | INTEGER | create 为 NULL；update/delete 为本地 `server_version` |
| `idempotency_key` | TEXT NOT NULL | 本地去重键；默认等于 `op_id`，不发送给服务端 |
| `batch_id` | TEXT | 首次进入批次时写入；重试/进程恢复复用；未入批为 NULL |
| `state` | TEXT NOT NULL | `pending/inflight/done/conflict/failed` |
| `attempts` | INTEGER NOT NULL DEFAULT 0 | 已尝试次数 |
| `next_retry_at` | INTEGER NOT NULL DEFAULT 0 | epoch millis；0 表示可立即重试 |
| `created_at` | INTEGER NOT NULL | epoch millis |
| `last_error_code` | TEXT | 最近一次稳定错误码/原因，不含 payload |

约束与索引：

- `UNIQUE(owner_id, object_type, object_id) WHERE state='pending'`（SQLite partial index），
  保证同一对象最多一个待推送意图；
- `(owner_id, state, next_retry_at)` 索引用于 worker 选批；
- `batch_id` 索引用于进程重启后找回同批。

`batch_id` 是超出服务端字段列表的**本地持久化列**，原因是服务端只按 batch 幂等；
进程在“请求已提交、响应丢失”时，必须用同一 `batch_id` 重试，不能新造批次把同一批再发一次。

#### `sync_state`

| 列 | 说明 |
| --- | --- |
| `owner_id` TEXT PK | 每 owner 一行 |
| `cursor` INTEGER NOT NULL DEFAULT 0 | 服务端 `next_cursor`，只进不退 |
| `last_push_at` | 毫秒；成功 push 批后更新 |
| `last_pull_at` | 毫秒；成功应用一页后更新 |
| `device_id` TEXT NOT NULL | 安装级 UUID；不采集硬件标识；跨 owner 同值 |

#### `sync_tombstones`

| 列 | 说明 |
| --- | --- |
| `owner_id` | 分区 |
| `object_type` | 五类 |
| `object_id` | 服务端 UUID |
| `deleted_at` | 毫秒 |
| `version` | 删除后的服务端版本 |
| PK | `(owner_id, object_type, object_id)` |

#### `sync_conflicts`

冲突不能只留一个错误码；需要保留双方数据供 UI：

| 列 | 说明 |
| --- | --- |
| `owner_id` / `object_type` / `object_id` | 对象 |
| `local_payload_json` | 发起冲突的本地 payload |
| `remote_payload_json` | 冲突拉取得到的服务端 payload（无 payload 时为 NULL） |
| `local_base_version` / `server_version` | 版本 |
| `reason` | `version_mismatch/already_exists/not_found/remote_deleted/...` |
| `created_at` | 毫秒 |
| `state` | `open/resolved` |

### 3.4 删除表达

- 选择 **tombstone**，不给每张内容表加 `deleted` 列。
- 本地删除在**同一 Room 事务**中：删除内容行 + 写 `sync_outbox(op=delete, payload=NULL,
  base_version=server_version)` + 写/更新 `sync_tombstones`（版本用当前 `server_version`，
  服务端确认后回填新版本）。
- pull 到 `deleted=true`：写 tombstone，删除本地内容行；不把旧 payload 重新插入。
- 客户端收到 `version <= tombstone.version` 的旧 create/update 时直接丢弃；大于 tombstone.version
  的变更才允许恢复。

### 3.5 Room 版本与迁移

当前 `DeskDatabase` 为 **version 4**；目标为 **version 5**，只增表/列并重建需要复合主键的表。

- 五张内容表增加 `owner_id`、`client_id`、`server_version`、`updated_at`；
  `settings`/`daily_work_times` 增加可空 `time_zone`。
- 主键调整：
  - `tasks`、`blocks`、`checkins`：`(owner_id,id)`；
  - `settings`：`(owner_id,id)`（id 仍为 1）；
  - `daily_work_times`：`(owner_id,date)`。
- 因为 SQLite 不支持直接改主键，迁移采用“建新表 → 复制 → 校验计数/外键引用 → drop 旧表 →
  rename”的受控重建；全程在一个事务中，失败回滚。
- 旧数据：
  - `owner_id='guest'`；
  - UUID 主键的 task/block/checkin：`client_id=主键`；
  - 非 UUID 主键：`client_id=NULL`，保留本地、本轮不推送，并在迁移报告中计数；
  - `server_version=0`；
  - `updated_at` 用现有 `created`/`start`/`completedAt`/0 回填；
  - `time_zone=NULL`，不猜测。
- `settings`/`daily_work_times` 的确定性 `client_id` 在迁移后由本地修复例程生成；
  在生成前保持 `client_id=NULL`，不进入 outbox。
- 新增 `sync_outbox`、`sync_state`、`sync_tombstones`、`sync_conflicts`；
  `task_reminders`、`diaries`、`ui_preferences`、agent 表不动。
- 保留 `exportSchema=true`，提交 version 5 schema；`MIGRATION_4_5` 用
  `MigrationTestHelper` 做 v4 样本 → v5 的迁移测试；不使用 `fallbackToDestructiveMigration`。
- 不使用 `db push`/重建数据库；迁移只在 Room 内完成，服务端 schema 不在本设计内。

## 4. Push 协议

### 4.1 写入与出队

1. 所有会改变同步对象的本地写必须在**一个 Room 事务**中完成：内容表 + outbox + tombstone
   （删除时）。
2. 事务提交后由 worker 触发，不在 UI 线程发网络请求。
3. 同一对象在 `pending` 状态再次被修改时：
   - `pending create` + 后续修改：合并为最新 payload，仍为 create，`base_version=null`；
   - `pending update` + 后续修改：合并 payload，保留第一次的 `base_version`；
   - `pending create` + 删除：撤销 create，不产生服务端对象；
   - `pending update` + 删除：改为 delete，保留 `base_version`；
   - 已有 `conflict` 的对象不再自动合并新写入，进入冲突 UI（§6）。
4. 合并只在同一事务内完成，避免“旧 payload 仍被 worker 取走”。

### 4.2 批次

- 每个批次新生成 `batch_id`（UUID）；选中 outbox 行后，把同一个 `batch_id` 写回这些行。
- 同一批重试/进程恢复必须复用 `batch_id` 和**同一规范化 JSON body**；不得重新序列化出
  不同键顺序/空格，避免服务端指纹不一致 409。
- `device_id` 是安装级持久 UUID；不采集硬件序列号、MAC 或广告 ID。
- 选批上限：
  - 最多 200 项（服务端上限）；
  - 总 JSON body 控制在 200KiB 以内（低于服务端全局 body 限制，留出重试/网络余量）；
  - 单项 payload ≤32KiB（服务端前置校验）；超限项直接标记 `failed`，不阻塞其他项。
- body 形状严格按服务端契约：

```json
{
  "batch_id": "<uuid>",
  "device_id": "<uuid>",
  "mutations": [
    {
      "object_type": "task",
      "object_id": "<uuid>",
      "op": "update",
      "expected_version": 3,
      "payload": {}
    }
  ]
}
```

- `delete` 的 `payload` 省略或为 null；`create` 的 `expected_version=null`。

### 4.3 结果处理

| 服务端结果 | 本地动作 |
| --- | --- |
| item `applied` | 更新内容行 `server_version`；`server_version=0` 的 create 也落新版本；outbox `done`；删除对应 tombstone 的旧版本；更新 `last_push_at` |
| item `conflict` | outbox `conflict`；保留 payload；写/更新 `sync_conflicts`；触发针对性拉取（§5.4）；不自动改本地内容 |
| item `rejected` | outbox `failed`，记录 `reason`（如 `unsupported_object_type`、`payload_required`）；不做盲目重试，UI 显示需修复 |
| 整批 `status=partial` | 按 items 逐项处理；不整批重放 |
| 整批 409（同 batch 异体） | 停止该批；不改本地内容；标记批次错误并上报；下一次用新 batch_id 重新选批（需先排查为何 body 变化） |
| HTTP 400/413/422 | 视为请求/单项格式问题；停止该批，标 `failed`，提示修复；不自动重发 |
| HTTP 401 | 暂停 worker；交由 T31 refresh/session；outbox 不丢；登录失效时暂停同步 |
| HTTP 403 | 停止该 owner worker，清理在途状态；不重试到别的 owner |
| HTTP 429/5xx/网络超时 | attempts+1，计算 `next_retry_at`，保持 pending；不改变 payload/base_version |
| 响应丢失/进程被杀 | 若 outbox 已有 `batch_id` 且为 `inflight`，恢复为 `pending` 并用原 `batch_id` 重试；服务端按 batch 回执 |

- 对 `applied` 的本地更新必须仍校验 `owner_id + sessionId`；旧 owner 的迟到响应直接丢弃。
- `server_version` 只由 push 回执或 pull 的 `version` 更新；客户端不得自增。
- 不按客户端字符串直接改积分/VIP；这些字段不进同步 payload。

## 5. Pull 协议

### 5.1 基本流程

1. 从 `sync_state(owner).cursor` 开始（无记录为 0），`limit=100`（服务端会 clamp 到 1..200）。
2. `GET /sync/pull?cursor=&limit=`；服务端按 `sync_changes.seq` 升序返回
   `changes[]`、`next_cursor`、`has_more`。
3. 一页在**一个 Room 事务**中应用；成功后才把 `cursor=next_cursor` 写入 `sync_state`。
4. `has_more=true` 继续下一 页；否则结束。
5. 不按客户端时间猜 cursor；cursor 是服务端 `seq`，不是对象 `version`。

### 5.2 变更应用

对每条 change：

- 若 `deleted=true`：插入/更新 tombstone，删除本地内容行；若本地有 pending/conflict，
  不自动删除，转为冲突。
- 若本地有 tombstone 且 `change.version <= tombstone.version`：丢弃（防复活）。
- 若本地有 pending 或 conflict 的同对象变更：不静默覆盖 outbox；把服务端 payload 写入
  `sync_conflicts.remote_payload_json`，保持 pending/conflict，进入冲突处理。
- 否则按 §3.2 映射写入 Room，更新 `server_version=change.version`、`updated_at=now`、
  owner 不变；不把 `client_id` 改写。
- 同一对象在一页内出现多次时，按 `seq` 顺序应用，后一条覆盖前一条；版本必须递增。
- `payload` 为 null 的 delete：只 tombstone，不解析 payload。

### 5.3 顺序决定

- **先 push 后 pull**：本地 outbox 代表用户明确写入；先让服务端判定版本冲突，再拉取远端
  变化。原因：如果先 pull 再 push，pull 到的新版本会让本地 pending 的 `base_version`
  立即过期，冲突面更大；先 push 能用服务端版本给出精确冲突，随后 pull 补齐远端对象。
- 但登录后的首次同步例外采用 **pull 基线 → guest 合并 → push**（§7）；否则 guest 合并
  可能把服务端已存在的对象再次 create。
- push 完成后立即 pull 一页以上，直到 `has_more=false`；不能只 push 不 pull，否则其他设备
  的变更永远看不到。

### 5.4 冲突对象的定向拉取

服务端 push 的 conflict 只返回 `server_version` 和 `reason`，**不返回当前 payload**；pull
接口也没有“按 object_id 取当前对象”的参数。因此：

1. conflict 时把 outbox 置为 `conflict`，不立即重试。
2. 为该对象执行一次**定向修复拉取**：从 `cursor=0` 分页扫描到当前末尾，只挑选该
   `(object_type,object_id)` 的最新 change，写入 `sync_conflicts.remote_payload_json`。
3. 扫描结束后恢复原 `cursor`（不能把全量扫描的 cursor 当作增量游标）。
4. 如果对象在服务端已不存在（只有 tombstone），remote payload 为 NULL，按“远端删除”处理。
5. 该全量扫描只用于冲突修复，不在每次普通 pull 中使用；规模变大时需要服务端提供
   `GET /sync/objects/{object_type}/{object_id}` 或 push conflict 直接带 payload（§13）。

## 6. 冲突规则

### 6.1 权威边界

服务端权威的只有：**归属用户、对象类型/UUID、当前版本、删除 tombstone、批次幂等和
RLS/事务**。服务端**不校验** payload 内部字段，因此不能声称“服务端保证 locked/done”。

客户端对以下字段采用保守的“受保护字段”策略：

- `task.done`、`block.locked`、`block.done`、`checkin`、`availability` 的日期/时区、
  `settings` 的作息时间：不允许静默 LWW 覆盖；
- `points`、`VIP`、钱包：**不在同步白名单**，只通过账户 API 读取，客户端不能写入；
- 删除：不自动复活，不自动覆盖本地未推送编辑。

### 6.2 按对象规则

| 对象 | 可自动合并的字段 | 必须人工确认的字段 | 规则 |
| --- | --- | --- | --- |
| `task` | 无（整对象版本冲突） | 标题/备注/截止/工时/分类/重要性/完成 | 版本不一致 → conflict；文本字段可在 UI 逐字段选择“本地/远端”，结构字段必须整对象选择；`done` 不自动改 |
| `block` | 无 | start/end、locked、done | 时间变更不自动合并；`locked/done` 不一致必须提示，不能自动解锁/改完成 |
| `checkin` | 相同 payload 的重复 create | 同 ID 不同 payload | 追加型；同 ID 同 payload 视为已应用；不同 payload 为 conflict，不覆盖、不删除旧 checkin |
| `availability` | 无 | date/start/end/time_zone | 时区/日期不一致即冲突；不把 A 时区的可用时间静默应用到 B |
| `settings` | 无 | start/end、time_zone | 整对象冲突；不自动跨时区改写作息 |

### 6.3 删除 vs 修改

- 远端 `deleted` 且本地无 pending：**删除优先**，本地删除并写 tombstone。
- 远端 `deleted` 且本地有 pending/conflict：**不删除本地**；进入冲突，显示“远端已删除”。
  UI 选择：
  1. 放弃本地修改；
  2. 保留为新对象（生成新 UUID，重新 create；旧 ID 仍为 tombstone）；
  3. 取消，稍后处理。
- 本地删除且远端随后修改：本地 delete 先按版本 push；若服务端返回 conflict，保留本地
  tombstone 意图并进入冲突；不能因为远端修改而自动复活本地内容。
- 旧离线副本的 create/update 如果版本 ≤ tombstone.version，直接丢弃，不复活。

### 6.4 时区/日期边界

- 瞬时（deadline、block start/end、checkin completed_at）统一 epoch millis，传输不随设备时区改变。
- 业务日/可用时间使用 `YYYY-MM-DD` + `start_minute/end_minute` + IANA `time_zone`；
  不做静默 DST 修正；无效本地时刻拒绝并让用户选择。
- `settings` 的 start/end 是本地墙钟；`time_zone` 不同即冲突，不自动换算。
- 服务端业务日规则（`BUSINESS_TIMEZONE`）只用于签到等业务，不用于改写客户端本地日程。

### 6.5 冲突 UI

- 冲突列表按 owner 展示对象类型/标题/本地修改时间/远端版本/原因。
- 单对象详情：左右对比本地与远端 payload；文本字段可逐字段选择，结构字段整对象选择。
- 批量操作只允许“全部保留本地为新建”/“全部接受远端”，并二次确认；不能默认丢弃。
- 未解决冲突的对象不再进入 outbox 自动重试；用户解决后写新 outbox（或标记 done）。
- 解决事务必须同时更新内容行、`server_version`、outbox/conflict 状态，失败整体回滚。

## 7. 访客 → 账户合并

### 7.1 触发与前提

- 只在**登录成功或已有会话 restore 成功**、且 `AccountSession.begin(accountSession)` 成功后触发。
- 先完成账户 **pull 基线**（cursor=0 到末尾，或已有 cursor 的增量）；pull 失败则不合并。
- 显示访客任务/安排/签到/可用时间数量；用户确认后才执行。注册不自动登录，不触发合并。
- 访客与账户的 `owner_id` 分别为 `guest` 和认证用户 UUID。

### 7.2 决定：移动，不复制

- 在**一个 Room 事务**中把访客的同步对象 `owner_id` 从 `guest` 改为账户 userId；
  保留 `id/client_id` 和服务端 object_id，不生成第二份。
- 同一事务为每个移动对象写 `outbox create`（`base_version=null`，`server_version=0`
  若之前未推送）。若账户基线中已存在同一 object_id，**不移动该对象**，进入冲突清单。
- `task_reminders`、`diaries` 也随 owner 移动（本地-only，不写 outbox），保证登录后
  T26 的 active owner 和日记仍可见；若账户已有同 `(task,date)`，列为冲突，不静默覆盖。
- `ui_preferences` 的 `device` 行不移动；用户偏好是否迁移另议（本轮不迁移）。
- 移动后 guest 工作区为空；退出后不再保留一份 guest 副本。这是明确的产品决定：
  **访客数据被账户接管，退出后通过重新登录账户访问，不在 guest 继续保留**。
- 拒绝合并/取消确认：guest 数据保持原样，账户同步照常进行，不删除任何本地数据。

### 7.3 去重与冲突

- 同 `client_id`/object_id 已存在：比较 payload；完全一致则跳过移动并标记已合并；
  不一致则保留两边，进入冲突 UI，不重复创建。
- 任务被移动时，其 blocks/checkins 一并移动；若子对象冲突，整个任务组不移动，提示用户。
- 合并失败：Room 事务回滚，guest/account 都不变；outbox 不残留 create；用户可重试。
- 合并成功后，后续 worker 只处理账户 owner；guest worker 不再存在。

### 7.4 UI

- 合并确认页：数量、最近修改时间、预计上传条数、可能冲突数；按钮“合并 / 稍后 / 取消”。
- 完成后 toast/列表显示成功数、冲突数；失败显示可重试错误，不显示 payload 正文。
- 冲突项进入 §6.5 的统一冲突页面。

## 8. 账户隔离与缓存

### 8.1 分区键

- 所有同步内容、outbox、state、tombstone、conflict 均以 `owner_id` 为第一分区键：
  `guest` 或服务端 userId。
- 所有 DAO 查询/更新必须带 `owner`；不允许无 owner 的 `SELECT * FROM tasks` 参与同步，
  也不允许跨 owner 的 block/checkin 外键。
- `settings`/`daily_work_times` 的复合主键包含 owner；任务/块/签到也使用 `(owner_id,id)`。
- `sync_state.device_id` 是安装级值，但 cursor/worker 按 owner 独立。

### 8.2 登录/换号/退出

- 登录成功：`AccountSession.begin` + 账户基线 pull + 访客合并（可选）+ 启动该 owner worker。
- 换号/退出：立即取消旧 owner 的 WorkManager unique work；把 in-flight 结果标记为不可应用；
  清空当前 UI 的内存快照；旧 owner 的 outbox/cursor 保留但不运行。
- 捕获 T31 的 `sessionId` 与 owner：push/pull 每个响应应用前核对
  `currentSessionId` 与 `owner`；不等则丢弃，不写 Room/不推进 cursor。
- 任何网络请求仍由 T31 的 ApiClient 负责 token refresh；同步层不保存 token、不拼 owner header。

### 8.3 缓存清理

- **默认不删除**旧 owner 的本地数据：按 owner 保留，UI 不展示，只有同一 owner 重新登录可见。
  这样离线编辑/未解决 outbox 不会因退出而丢失。
- 提供“清除此账户本地数据”显式操作：删除该 owner 的内容/outbox/state/tombstones/conflicts，
  保留 guest；需二次确认并提示未同步数据会丢失。
- 清除 token 不清 guest 数据，也不删除账户缓存；guest 清理只能由用户独立操作。
- `agent`/`diaries`/`reminders` 同样按 owner 隔离；diaries/reminders 本轮不参与同步。
- Room 本身不是加密数据库；本文不声称静态加密，只要求应用沙箱 + owner 过滤；如需更强保护另立加密方案。

## 9. 离线、重试与调度

### 决定

- 使用 **WorkManager**（Android Jetpack）做后台同步；v1 不引入前台服务。
- unique work name：`sync-<owner_id>`；同一 owner 串行，不同 owner 不并行。
- 约束：`NetworkType.CONNECTED`；不做“仅 WiFi”默认，演示环境可能用热点。
- 触发：
  1. 本地写事务后 debounce 1s 请求一次同步（不是每个字段都发）；
  2. App 启动/回到前台；
  3. 网络恢复；
  4. 周期任务每 15 分钟（WorkManager 最小周期），只在有 pending 时实际发请求；
  5. 冲突页/同步页手动重试。
- 退避：30s × 2^attempts，上限 6h，加 ±20% 抖动；`next_retry_at` 持久化。
- 429 优先按服务端 `Retry-After`（若有）覆盖退避；没有则按上式计算。
- 进程被杀：
  - outbox 与 batch_id 持久化；
  - 启动时把 `inflight` 且超过租约（例如 5 分钟）的行恢复为 `pending`，复用原 batch_id；
  - 若服务端已处理，同 batch_id 返回 replayed，客户端按 items 落 done；
  - 不因进程重启清空 pending/conflict。
- 飞行模式：worker 保持 pending，不消耗 attempts；网络恢复后再计时。
- 手动重试：只重置 `next_retry_at=0`，不改 payload/base_version；conflict/failed 由用户解决。
- 本地写失败（Room 事务失败）：不产生 outbox；UI 报错，保持原数据。

## 10. 错误与可观测性

| 情况 | 客户端行为 | 是否自动重试 |
| --- | --- | --- |
| 401 UNAUTHENTICATED / 会话切换 | 暂停该 owner worker；T31 refresh；登录失效则 gate LOGIN；outbox 保留 | 否，等重新登录 |
| 403 FORBIDDEN（owner 不符） | 停止 worker，清 in-flight；不向其他 owner 重发 | 否 |
| 400/413/422（payload/格式/超限） | 批或单项 `failed`；显示可操作错误；提示缩小/修复 | 否 |
| 409（同 batch 异体） | 停止该批；记录批次错误；排查后新 batch | 否 |
| 429 RATE_LIMITED | 退避；保留 pending | 是 |
| 5xx/UPSTREAM_UNAVAILABLE | 退避；保留 pending | 是 |
| 网络不可达/超时 | 退避；保留 pending；不错误地标 conflict | 是 |
| 服务端 item conflict | 转 conflict + 定向 pull；不自动改内容 | 否，等用户 |
| 响应无法解析/未知状态 | 保留 pending/inflight，按未知处理；不猜测成功 | 是（保守退避） |

日志与指标：

- 只记录 `owner` 的散列/短标识、`op_id`、`object_type`、`op`、`result`、HTTP 状态、
  `request_id`（若响应有）、耗时、attempts；**不记录 prompt/response/payload 正文、
  token、验证码、日记内容、备注、邮箱**。
- 指标：pending 数、conflict 数、failed 数、最老 pending 年龄、最近 push/pull 时间、
  429/5xx 计数；不把指标标签做成高基数（不把 object_id 当标签）。
- 用户可见状态：同步中/已同步/有待处理冲突/失败；失败页提供重试与详情（不含正文）。

## 11. 迁移与回滚

### 迁移步骤（设计）

1. 生成并提交 version 5 Room schema；评审字段/索引/主键。
2. 编写 `MIGRATION_4_5`：建新表、复制、校验行数与引用、drop 旧表、rename；单事务。
3. 迁移后修复例程：为 `settings`/`daily_work_times` 生成确定性 `client_id`；
   统计非 UUID 主键的 task/block/checkin，标记 local-only。
4. 首次启动只读校验：owner 列非空、复合主键、`server_version>=0`、tombstone 无重复；
   失败进入“只读/修复”状态，不自动删除用户数据。
5. 迁移测试：v4 样本库（有任务/块/签到/设置/可用时间、无同步列）→ v5；断言数据、主键、
   索引、owner=guest、client_id/server_version 回填；`MigrationTestHelper` 跑通。
6. 不使用 destructive migration；不在迁移中清空 outbox（v4 没有 outbox）。

### 回滚

- Room 不自动降级；v5 打开失败时保留数据库文件，进入只读/诊断，不执行 `fallbackToDestructiveMigration`。
- 迁移失败：事务回滚，旧表保留；提供“导出诊断/重试迁移”，不自动清库。
- 发布回滚只回滚 App 版本时，v5 数据不能被旧 v4 读取；需保留升级前备份/由用户选择清除本地数据。
- 清 outbox 的条件：用户显式“清除此账户本地数据”，或 outbox 行已确认损坏且用户确认；
  不以“登录失败/换号”自动清空。
- 服务端迁移/回滚不在本设计范围。

| 离线改 → 上线 | 改动在 outbox；上线后 push applied；不重复 |
| 两端改同一任务 | 两端都看到冲突；本地输入不丢；用户选择后收敛 |
| A 删除、B 离线修改 | B 上线显示“远端已删除”；不自动复活；可选新对象 |
| guest→A | 确认后 guest 记录归 A；不重复；guest 清空；退出后 A 数据仅 A 可见 |
| A→B 切换 | B 不看到 A；A 的迟到 push/pull 丢弃；A outbox/cursor 保留 |
| 进程被杀 | 重启后 pending 恢复；同 batch 幂等；不重复通知/对象 |
| 200 项/32KB 边界 | 200 项内成功；超限项失败可定位；总 body 不触发 413 |

## 13. 开放问题（给 Bottledkzk）

1. **cursor 保留期**：`sync_changes` 的 `seq` 是否长期保留？客户端离线超过保留期后，
   `cursor` 已失效时服务端是否返回明确错误/要求重置 cursor？本设计默认“cursor 只进不退”，
   需要服务端确认清理策略和重置协议。
2. **冲突 payload**：push conflict 目前只返回 `server_version/reason`，不返回当前 payload；
   本设计用 cursor=0 定向扫描。是否愿意在 conflict item 中增加当前 payload，或增加
   `GET /sync/objects/{type}/{id}`？这会影响冲突 UI 的成本。
3. **settings/availability 字段**：服务端把 payload 当 opaque JSON；是否确认
   `start_hour/end_hour/start_minute/end_minute/date/time_zone` 的客户端字段名，以及
   `settings` 是否包含 `ui_preferences` 的主题/星期偏好？本设计选择只同步 `SettingRow` 作息，
   不同步设备偏好。
4. **reminders/diaries**：本设计明确“本轮本地-only”。若后续要进白名单，需要服务端新增
   类型、RLS/字段约束、payload 上限和隐私评审；请确认优先级和保留期。
5. **批次/重试上限**：客户端拟 200 项、总 body 200KiB、退避 30s..6h；服务端是否接受
   这个总 body 预算？429 是否稳定返回 `Retry-After`？
6. **时区**：availability/settings 的 `time_zone` 是否由客户端作为 payload 字段传输？
   服务端业务日时区不参与个人日程换算，请确认不会在服务端按 `BUSINESS_TIMEZONE` 改写这些对象。
7. **删除保留**：`sync_changes.deleted` 是否永久保留 tombstone？客户端 tombstone 的清理
   是否必须等 cursor 超过服务端保留期，还是可以本地永久保留？

以上问题不阻塞本设计评审；实现 PR 前需要服务端确认 1–3 和 5，4 单独立项，6/7 在联调前确认。
