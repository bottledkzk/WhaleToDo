# 订单与商品字段建议（Weiding → Bottledkzk）

日期：2026-10-25　状态：**建议稿，未改动任何现有迁移**
依据：交接文档第 7 节末尾「订单/支付字段待 Weiding 建议另作迁移」；本轮只提字段与约束，不建表、不改表。

## 1. 现有可复用的部分

| 已有表/机制 | 订单可复用方式 |
| --- | --- |
| `point_wallets` / `point_ledger` | 支付成功后发积分走**同一账本**（`type=award`，`reason=order:<order_id>`），不新建余额表 |
| `entitlements` | VIP 到期时间写这里（`kind='vip'`、`source_order_id`），已存在无需改 |
| `idempotency_receipts` | 下单幂等可用 `scope='v1:order:<user_uuid>'`，与我的实现一致，不必给 `orders` 再加幂等键 |
| RLS 约定 | 内容表用 `owner_scope`（`user_id = current_setting('app.user_id')`），订单表建议同样处理 |

## 2. 建议新增的三张表

### 2.1 `products`（全局，无 RLS）

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `product_id` | varchar(32) | 主键，如 `vip_30d` / `points_300` |
| `title` | varchar(64) | NOT NULL |
| `price_minor` | integer | NOT NULL, `CHECK (price_minor >= 0)`（最小货币单位） |
| `currency` | char(3) | NOT NULL, `CHECK (currency = upper(currency))` |
| `vip_days` | integer | NOT NULL DEFAULT 0, `CHECK (vip_days >= 0)` |
| `points` | integer | NOT NULL DEFAULT 0, `CHECK (points >= 0)` |
| `active` | boolean | NOT NULL DEFAULT true |
| `created_at` | timestamptz(3) | NOT NULL DEFAULT now() |

### 2.2 `orders`（用户数据，建议启用 RLS）

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | uuid | 主键 |
| `user_id` | uuid | NOT NULL REFERENCES users(id) ON DELETE CASCADE |
| `product_id` | varchar(32) | NOT NULL REFERENCES products(product_id) |
| `amount_minor` | integer | NOT NULL, `CHECK (amount_minor >= 0)` —— **下单时从 products 快照，客户端传值一律忽略** |
| `currency` | char(3) | NOT NULL |
| `status` | varchar(16) | NOT NULL, `CHECK (status IN ('PENDING','PAID','CLOSED','REFUNDED'))` |
| `environment` | varchar(16) | NOT NULL（**无默认值**，由服务端可信配置显式写入，缺失则拒绝启动）, `CHECK (environment IN ('mock','production'))` |
| `created_at` | timestamptz(3) | NOT NULL DEFAULT now() |
| `product_snapshot` | jsonb | NOT NULL，下单时的**不可变商品快照**：`{title, price_minor, currency, points, vip_days}` |
| `paid_at` | timestamptz(3) | 可空 |

索引：`(user_id, created_at DESC)`。
**不建议**再加 `(user_id, idempotency_key)` 唯一键——幂等统一由 `idempotency_receipts` 承担，
避免两套幂等语义（这也是你在第 7 节里定的方向）。

### 2.3 `payment_events`（支付回调，无 user_id，经订单归属）

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | uuid | 主键 |
| `provider` | varchar(16) | NOT NULL，如 `mock` |
| `event_id` | varchar(64) | NOT NULL |
| `order_id` | uuid | NOT NULL REFERENCES orders(id) ON DELETE CASCADE |
| `status` | varchar(16) | NOT NULL, `CHECK (status IN ('succeeded','failed','refunded'))` |
| `amount_minor` | integer | NOT NULL |
| `payload_hash` | char(64) | NOT NULL（回调原文摘要，不存原文） |
| `received_at` | timestamptz(3) | NOT NULL DEFAULT now() |

唯一键：**`UNIQUE (provider, event_id)`** —— 重复回调不重复发权益。
RLS：通过 `EXISTS (SELECT 1 FROM orders o WHERE o.id = payment_events.order_id AND o.user_id = current_setting(...))`，
与 `sync_mutations` 的 `owner_batch_scope` 写法同构。

## 3. 支付成功的事务边界（关键）

一个事务内完成，任一步失败整体回滚：

```
BEGIN;
  UPDATE orders SET status='PAID', paid_at=now()
   WHERE id=$order AND status='PENDING';          -- 影响 1 行，否则视为重复回调/异常状态
  INSERT INTO payment_events (...) VALUES (...);  -- UNIQUE(provider,event_id) 兜重复
  INSERT INTO point_ledger (...) VALUES (...);    -- 仅当 product.points > 0，type='award'
  UPDATE point_wallets SET available = available + $points WHERE user_id=$user;  -- 与流水同事务
  INSERT INTO entitlements (...) VALUES (...);    -- 仅当 product.vip_days > 0
COMMIT;
```

顺序建议：先 `UPDATE orders`（拿状态机唯一性）→ 插回调事件 → 发积分 → 发权益。
积分与权益都写在同一事务里，避免"钱付了但权益没到账"。

## 4. 与客户端/接口的约定

| 项 | 约定 |
| --- | --- |
| 下单请求 | 只传 `product_id`；金额、币种、权益全部由服务端商品快照决定 |
| 订单查询 | `GET /orders/{id}` 归属校验失败与不存在统一返回 403（防枚举） |
| 模拟支付 | `PAYMENT_PROVIDER=mock` 只允许 `NODE_ENV=test|demo`；`orders.environment` 记录来源，便于审计 |
| 回调校验 | 校验 `amount_minor`/`currency` 与订单一致，不一致 400 且订单保持 PENDING |

### 关于查询参数类型

评审建议：为流水/变更这类分页查询加统一 schema 约定，保证参数类型稳定。
落地方式（已在签到流水实现）：
- 游标只用**纯数字文本 + uuid 两段**，进入 SQL 前校验为安全整数与合法时间；
- 数值参数一律转成 Date/uuid 再传，避免 `number::timestamptz` 这类隐式转换错误；
- 分页排序与游标谓词使用同一复合元组（如 `(created_at, id)`），保证跨页不丢不重。

## 5. 已确认结论（2026-10-25 评审）

| # | 结论 | 对实现的影响 |
| --- | --- | --- |
| 1 | **不建 `product_prices`**。下单时把商品名称/金额/币种/积分/VIP 天数写入 `orders.product_snapshot`；发权益读**订单快照**，绝不读可能已改价的 `products` | 订单表加 `product_snapshot jsonb NOT NULL` |
| 2 | 首版**只做一次全额退款**，不做退款单、不做部分退款 | 见 5.1 的退款事务 |
| 3 | `orders` **不加 `deleted_at`**；审计订单保留。现有 `users ON DELETE CASCADE` 与审计目标冲突，后续迁移改为保留/限制删除，账户删除另设计匿名化 | 本稿不改已有迁移，仅记录冲突 |
| 4 | `environment` 由**服务端可信配置**写入，不默认 `production`、不接受客户端决定；未来真实支付与 mock 须分库/分角色隔离，不以字段代替隔离。本轮只启用 mock | 配置项显式指定，缺省拒绝启动 |

### 5.1 退款事务（首版规则）

一个事务内完成，任一步失败整体回滚：

```text
BEGIN;
  UPDATE orders SET status='REFUNDED'
   WHERE id=$order AND status='PAID';            -- 影响 1 行，否则退出（重复回调/状态不符）
  INSERT INTO payment_events (... status='refunded' ...);   -- UNIQUE(provider,event_id) 兜重复
  INSERT INTO point_ledger (... type='adjust', available_delta=-points, reason='refund:<order_id>');
  UPDATE point_wallets SET available = available - points WHERE user_id=$user;
  UPDATE entitlements SET expires_at = now()      -- 仅撤销**该订单来源**的 VIP（source_order_id=$order）
   WHERE source_order_id=$order AND expires_at > now();
COMMIT;
```

规则：
- 若积分已被消费/预占导致可用不足 → **拒绝退款**并保持原状态，不能扣成负数
- 反复回调不重复回收（唯一退款事件）
- 只撤销该订单发放的权益，不影响其他订单
