# 接口冻结建议（Weiding）

日期：2026-10-23　状态：**提案，待 Bottledkzk 评审**
范围：仅覆盖分工方案中 Weiding 主责的部分（账户、签到积分、订单/支付、同步），以及双方共用的统一约定。
注意：本文件是讨论稿，**不修改 `doc/All`**；评审通过后再合并进《接口与数据契约草案》并升版本。

## 1. 后端选型建议

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| **TypeScript + Fastify + Prisma + PostgreSQL 16** | 鉴权/同步/订单都是 IO 与事务密集，生态成熟；Prisma 迁移文件可读，便于评审；可由 schema 生成 OpenAPI，客户端用 Retrofit 对接 | 与 Android 端语言不同，DTO 需对齐 | **推荐** |
| Kotlin + Spring Boot + Exposed | 与 `core` 同语言，数据类可对照 | 样板代码多，首轮迭代慢；Ktor/Exposed 迁移工具不如 Prisma 直观 | 备选 |

无论选哪个，**先冻结本文件第 2~4 节的字段、错误码与表约束**，语言选择不阻塞客户端联调（客户端只依赖 HTTP 契约）。

## 2. 统一约定（需冻结）

- 基址 `/api/v1`；私有接口带 `Authorization: Bearer <access_token>`。
- 时间：UTC ISO8601（`2026-10-23T05:00:00Z`）；业务日 `business_date` 由**服务端**按 `Asia/Shanghai` 生成。
- 响应包：
  - 成功 `{ "request_id": "...", "data": {...} }`
  - 失败 `{ "request_id": "...", "error": { "code": "VALIDATION_ERROR", "message": "...", "details": {...} } }`
- 写操作带 `Idempotency-Key`（UUID）；AI、签到、订单、同步批次**必须**幂等；同键不同体 → `CONFLICT`。
- 分页：`?limit=50&cursor=...`，返回 `{ "items": [...], "next_cursor": "..." }`；`limit` 上限 200。
- 错误码（首版固定 9 个，客户端做统一映射）：

| code | HTTP | 含义 |
| --- | --- | --- |
| `UNAUTHENTICATED` | 401 | 未登录 / 令牌过期 |
| `FORBIDDEN` | 403 | 已登录但无权访问该对象（越权） |
| `VALIDATION_ERROR` | 400 | 字段缺失或格式错误 |
| `INSUFFICIENT_POINTS` | 402 | 积分不足 |
| `RATE_LIMITED` | 429 | 触发频率/并发限制 |
| `CONFLICT` | 409 | 版本冲突、幂等键冲突、重复领取 |
| `UPSTREAM_UNAVAILABLE` | 503 | 上游（支付/模型）不可用 |
| `REQUEST_PENDING` | 202 | 请求已受理但结果未定（可查询） |
| `INTERNAL` | 500 | 未分类内部错误（不下发堆栈） |

## 3. 第一版接口（Weiding 主责）

| # | 方法与路径 | 请求（关键字段） | 响应（关键字段） | 备注 |
| --- | --- | --- | --- | --- |
| 1 | `POST /auth/register` | `username`, `password`, `display_name?` | `user_id` | 用户名唯一；不接受客户端指定 role/VIP |
| 2 | `POST /auth/login` | `username`, `password` | `access_token`, `refresh_token`, `expires_in`, `user` | 失败统一 `UNAUTHENTICATED`，不暴露账号是否存在 |
| 3 | `POST /auth/refresh` | `refresh_token` | 新 `access_token` + 轮换后的 `refresh_token` | 旧 refresh 立即作废；重放触发整串撤销 |
| 4 | `POST /auth/logout` | — | 204 | 撤销当前会话 |
| 5 | `GET /me` | — | `user{id,username,display_name,created_at}` | 最少资料 |
| 6 | `GET /me/entitlements` | — | `vip{active,expires_at}`, `daily_quota{points,claimed_today}` | 服务端裁决 |
| 7 | `GET /rewards/daily` | — | `business_date`, `claimed`, `reward{points}` | 由服务端时区决定 |
| 8 | `POST /rewards/daily/claim` | `Idempotency-Key` | `points_awarded`, `wallet{available,reserved}` | 唯一键 `(user_id,business_date,reward_type)`；与账本同事务 |
| 9 | `GET /wallet` | — | `available`, `reserved` | 只读本人 |
| 10 | `GET /wallet/ledger` | `limit`, `cursor` | `items[{id,type,delta,balance_after,request_id,created_at}]`, `next_cursor` | 分页 |
| 11 | `GET /products` | — | `items[{product_id,title,price_minor,currency,vip_days,points}]` | 价格服务端权威 |
| 12 | `POST /orders` | `product_id`, `Idempotency-Key` | `order_id`, `status`, `amount_minor`, `currency` | 金额/币种由服务端商品快照决定 |
| 13 | `GET /orders/{id}` | — | `order{...}` | 归属校验，越权 → `FORBIDDEN` |
| 14 | `POST /payments/mock/webhook` | `event_id`, `order_id`, `status`, `amount_minor` | 204 | **仅演示环境**（`PAYMENT_PROVIDER=mock`）；服务端校验金额与订单，重复事件幂等 |
| 15 | `POST /sync/push` | `batch_id`, `mutations[{object_type,object_id,op,version,deleted,payload}]` | `applied[]`, `conflicts[]` | `op ∈ create/update/delete`；版本不符 → `conflicts` |
| 16 | `GET /sync/pull` | `cursor`, `limit` | `changes[]`, `next_cursor`, `has_more` | 删除用 tombstone |
| 17 | `GET /health/live` `/health/ready` | — | `{status}` | 不返回内部拓扑 |

AI 相关（`/ai/*`）由 Bottledkzk 主责，本文件只约定它需要的上下文：`/me/entitlements` 与 `/wallet` 是它在调用前必须查询的两个接口。

## 4. 数据表最小字段（Bottledkzk 维护 schema，Weiding 实现业务）

| 表 | 关键字段 | 约束 |

## 6. 评审结论（2026-10-23，Bottledkzk 回复）

| # | 问题 | 结论 |
| --- | --- | --- |
| 1 | 后端选型与目录 | **TypeScript + Fastify + Prisma + PostgreSQL 定稿**。我负责账户、同步、签到与订单业务；**共享 schema／迁移由 Bottledkzk 统一维护、双方评审**。我先提交模块骨架与迁移建议，避免各自维护一套。 |
| 2 | 账本 type 与 AI 扣分时序 | `point_ledger.type` 首版保留 `award／reserve／settle／release／adjust`。AI 流程：鉴权与限额检查 → **事务预占** → 模型调用 → 成功结算／明确失败释放；**结果未知时保留状态并可查询**，不得直接重试扣费。两个余额／权益 GET 只供展示，不能替代服务端原子校验。 |
| 2b | 幂等键设计 | **`request_id` 不能在流水表设唯一**：需区分「关联请求」与「每次账本事件的幂等键」——改为 `request_id`（普通索引）+ `event_id`（唯一）。 |
| 3 | 同步对象与版本 | 首版覆盖 `task／block／checkin／availability`；`goal／stage` 后续扩展。`expected_version` 是**服务端对象版本**；拉取游标用**独立变更序列**，不按手机时间判定新旧。**手动块的 `locked` 必须同步保留**。**批次回执（sync_batches）与每项修改明细（sync_mutations）分开设计**。 |
| 4 | 业务时区 | 签到业务日默认 `Asia/Shanghai`，但必须**配置化**、不硬编码；事项展示时区继续跟随手机系统，两者分开。 |
| 5 | VIP 权益 | 暂只保留 VIP 身份与到期时间；具体积分与功能权益待定，不默认无限调用。有效权限统一由服务器返回。 |
| 6 | 模拟支付开关 | 可用 `PAYMENT_PROVIDER=mock`，但**仅演示/测试环境启用**；生产环境检测到 mock 配置应**拒绝启动**，并补访问控制。 |

### 据此对本文档的修订

1. **账本表**改为：`point_ledger(id, user_id, type, delta, balance_after, request_id, event_id, reason, created_at)`，唯一约束在 `(user_id, event_id)`，`request_id` 只建普通索引。
2. **同步表**拆成两张：
   - `sync_batches(id, user_id, batch_id, device_id, status, created_at)`，唯一 `(user_id, batch_id)`；
   - `sync_mutations(id, batch_id, object_type, object_id, op, applied_seq, result, created_at)`，记录逐项结果（applied／conflict／rejected）。
   - 响应相应拆为 `batch{...}` + `items[{object_id, result, server_version}]`。
3. **时区**：`BUSINESS_TIMEZONE` 走配置（默认 `Asia/Shanghai`），`daily_claims.business_date` 由服务端按该配置生成。
4. **模拟支付**：`PAYMENT_PROVIDER=mock` 仅在 `NODE_ENV=test|demo` 允许；启动时校验，生产直接抛错退出；mock webhook 额外要求内部签发的 `X-Mock-Token`。
5. **协作方式**：我用自己的 fork + 功能分支，阶段内多次提交，**完成一个可验收功能再请求合并**（不必重开 PR）；接口、后端与数据库测试不依赖模拟器，可与他的客户端并行推进。
