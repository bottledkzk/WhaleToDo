## 1. 架构先说清楚（1 分钟）

```text
Android App（Kotlin / Compose）
        │  HTTPS / JSON
        ▼
主服务 src/main.ts（账户、签到、钱包、订单、同步）
        │
        ├── PostgreSQL（生产/真库；RLS + 受限角色）
        └── 内存仓储（本地 demo，重启即清空）

AI 网关 src/ai/main.ts（同事负责，独立进程）
```

- 主服务与 AI 网关是两套进程；客户端只依赖主服务契约。
- 生产必须配置 `DATABASE_URL` 并走 Prisma；本地 demo 不配数据库时用内存仓储。
- 账户令牌不落明文：客户端 #25 用 Android Keystore AES/GCM 保存，服务端只保存会话摘要。

## 2. 演示主服务：账户、签到、钱包（3 分钟）

```bash
cd server
npm ci --ignore-scripts
npx prisma generate --schema prisma/schema.prisma
npm run typecheck      # 期望：0 诊断
npm test               # main：202；orders：217；email-account：210
PORT=8080 npm start
```

另开 PowerShell：

```powershell
$base = 'http://127.0.0.1:8080/api/v1'
$username = 'demo_user'
$password = 'S3cret-passw0rd'

$body = @{ username = $username; password = $password } | ConvertTo-Json -Compress
curl.exe -s -X POST -H 'Content-Type: application/json' --data $body "$base/auth/register"

$login = curl.exe -s -X POST -H 'Content-Type: application/json' --data $body "$base/auth/login" | ConvertFrom-Json
$token = $login.data.access_token

curl.exe -s -H "Authorization: Bearer $token" "$base/me"
curl.exe -s -X POST -H "Authorization: Bearer $token" "$base/rewards/daily/claim"   # 首次 201，再次 409
curl.exe -s -H "Authorization: Bearer $token" "$base/wallet"
curl.exe -s -H "Authorization: Bearer $token" "$base/wallet/ledger"
```

讲解要点：

- 注册只返回 `(id, username, display_name)`；运行角色没有写 schema 的权限。
- 签到第二次返回 **409 CONFLICT**，余额不变；唯一性由数据库约束兜底，不是应用层 `if`。
- 流水返回 `balance_after` 与 ISO8601 `created_at`，可以直接对账。

## 3. 邮箱账户演示（#24，评审意见已修复、待复审；约 2 分钟）

> #24 合并后接口才在 main。当前 main 只有用户名注册/登录；邮箱链路用测试或合并后的分支演示。
> **没有 SMTP**：现场无法收到验证码，下面的 `$code` 需要从测试投递钩子或后续邮件服务取得，不能假装已经收到。

```powershell
$base = 'http://127.0.0.1:8080/api/v1'
$email = 'demo@example.invalid'
$password = 'S3cret-passw0rd'

# 1) 发注册验证码（202；sent=false 表示冷却中）
$body = @{ email = $email; purpose = 'register' } | ConvertTo-Json -Compress
curl.exe -s -X POST -H 'Content-Type: application/json' --data $body "$base/auth/email/send-code"

# 2) 验证码换 ticket（ticket 60 秒内单次使用）
$code = '<从邮件/测试钩子取得的6位验证码>'
$body = @{ email = $email; code = $code; purpose = 'register' } | ConvertTo-Json -Compress
$verify = curl.exe -s -X POST -H 'Content-Type: application/json' --data $body "$base/auth/email/verify" | ConvertFrom-Json
$ticket = $verify.data.ticket

# 3) 带 ticket 注册（ticket 与 purpose/email 绑定；重复用/过期 400）
$body = @{ email = $email; ticket = $ticket; password = $password; display_name = '演示鲸鱼' } | ConvertTo-Json -Compress
curl.exe -s -X POST -H 'Content-Type: application/json' --data $body "$base/auth/register/email"

# 4) 邮箱登录
$body = @{ email = $email; password = $password } | ConvertTo-Json -Compress
curl.exe -s -X POST -H 'Content-Type: application/json' --data $body "$base/auth/login"
```

密码重置是同一套流程，只换 purpose：

```powershell
$body = @{ email = $email; purpose = 'reset' } | ConvertTo-Json -Compress
curl.exe -s -X POST -H 'Content-Type: application/json' --data $body "$base/auth/email/send-code"

$body = @{ email = $email; code = '<新验证码>'; purpose = 'reset' } | ConvertTo-Json -Compress
$resetTicket = (curl.exe -s -X POST -H 'Content-Type: application/json' --data $body "$base/auth/email/verify" | ConvertFrom-Json).data.ticket

$body = @{ email = $email; ticket = $resetTicket; password = 'N3w-secret-passw0rd' } | ConvertTo-Json -Compress
curl.exe -s -o NUL -w '%{http_code}' -X POST -H 'Content-Type: application/json' --data $body "$base/auth/password/reset"
# 期望 204；旧密码登录 401，新密码 200
```

讲解要点：

- 注册/重置都必须先 `verify` 拿 ticket；ticket 60 秒、单次消费、绑定 `purpose + email`。
- 注册时 ticket 消费与建用户在同一事务；邮箱冲突时 ticket 不消费。
- 重置不泄露账号是否存在：合法 ticket + 无账号邮箱也返回 204，并撤销该用户旧会话。
- 没有 SMTP 时只讲设计与测试结果；演示账号 seed 属于 T18，尚未实现。

## 4. 订单与 mock 支付演示（#23，评审意见已修复、待复审；约 2 分钟）

> #23 合并后接口才在 main；当前 main 没有 `/products`、`/orders`、`/payments/mock/webhook`。
> 内存模式默认没有商品数据，**T18 seed 商品前 `GET /products` 为空**，下不了单；可先用测试证据讲流程。

```powershell
$base = 'http://127.0.0.1:8080/api/v1'
$token = '<登录后的 access_token>'

# 1) 商品列表（公开；只返回 active）
$products = curl.exe -s "$base/products" | ConvertFrom-Json
$productId = $products.data.products[0].product_id

# 2) 下单（客户端只传 product_id；Idempotency-Key 防重复下单）
$body = @{ product_id = $productId } | ConvertTo-Json -Compress
$order = curl.exe -s -X POST -H "Authorization: Bearer $token" -H 'Idempotency-Key: demo-order-1' `
  -H 'Content-Type: application/json' --data $body "$base/orders" | ConvertFrom-Json
$orderId = $order.data.order.id
$amount = $order.data.order.amount_minor
$currency = $order.data.order.currency

# 3) mock 支付回调（登录态；金额/币种必须与订单快照一致）
$body = @{ event_id = 'evt-demo-1'; order_id = $orderId; status = 'succeeded'; amount_minor = $amount; currency = $currency } | ConvertTo-Json -Compress
curl.exe -s -X POST -H "Authorization: Bearer $token" -H 'Content-Type: application/json' --data $body "$base/payments/mock/webhook"
# 期望 {"data":{"ok":true,"replay":false}}；同一 event_id 再发一次应为 replay:true

# 4) 查订单、权益、钱包
curl.exe -s -H "Authorization: Bearer $token" "$base/orders/$orderId"
curl.exe -s -H "Authorization: Bearer $token" "$base/me/entitlements"
curl.exe -s -H "Authorization: Bearer $token" "$base/wallet"
```

讲解要点：

- 客户端只传 `product_id`，绝不传金额；下单时把商品价格/币种/VIP 天数写入不可变 `product_snapshot`。
- 支付回调先校验金额与币种，再走状态机；金额篡改返回 400，订单保持 PENDING，不发积分/VIP。
- `event_id` 有 `(provider, event_id)` 唯一键：同一订单重复回调返回 **200 replay**，不重复发奖；跨订单复用返回 **409 CONFLICT**。
- VIP 叠加按现有到期时间继续加，不是覆盖；`/me/entitlements` 能看到新的 `expires_at` 和积分余额。
- 真实支付回调需要特权上下文，当前 mock 是用户态模拟支付；商品后台/seed 留 T18，退款留 v1.1。

## 5. App 提醒演示（#25 评审意见已修复、待复审；#26 待评审；约 2 分钟）

> #25（账户接线）和 #26（提醒）合并后才能用 main 直接构建完整版本。当前可先用 #26 分支构建，提醒本身是本地数据，访客也能演示。

构建与安装：

```powershell
cd <repo>
$env:JAVA_HOME = '<JDK21>'

# 模拟器访问宿主机；真机把 10.0.2.2 换成电脑同一热点的局域网 IP
.\gradlew.bat :app:assembleDebug -PapiBase=http://10.0.2.2:8080/api/v1
adb install -r build\output\app\outputs\apk\debug\app-debug.apk
```

演示步骤：

1. 打开 App →「我的」→「自动提醒」；API 33+ 首次存在可调度提醒时申请通知权限（被拒不崩溃，开关保留）。
2. 新建/编辑一个任务，打开「事务通知」；`method` 选「消息」或「闹钟/两者」，`timing` 选「开始 / 结束 / 开始和结束」。
3. 把开始时间设到 1 分钟后（或设置未来截止时间作为无 block 回退），保存；保存安排会触发 `resyncAll`。
4. 等待通知；点击通知回到 MainActivity。到系统设置里查看两个渠道：
   - `task_reminders_message`：普通重要性（消息）
   - `task_reminders_alarm`：高重要性（闹钟/两者）
   - 旧 `task_reminders` 会在新版本首次启动时删除。
5. 可补充：完成/恢复任务、改期后重新保存、重启模拟器或改时区；`BOOT_COMPLETED` / `TIMEZONE_CHANGED` / `TIME_SET` / `MY_PACKAGE_REPLACED` 会重建 Alarm。

讲解要点：

- `ReminderPlanner` 是纯函数：start 取最早未来 block，end 取最晚未来 block end；无未来 block 回退 future deadline；只返回未来、去重升序。
- 调度不依赖通知权限；真正弹通知前才检查权限，避免权限变化后要重建 Alarm。
- 没申请 `SCHEDULE_EXACT_ALARM`；API 31+ 只探测 `canScheduleExactAlarms()`，能力不足用 inexact。
- **通知到点/重启重建尚未做真机验收**；答辩时如果没现场跑通，明确说“代码与编译已过，运行时验收待演示阶段”。

## 6. 真库与 CI 证据（1 分钟）

- 服务端 `npm test` 覆盖内存/HTTP；真实 PostgreSQL 由 CI `database` job 执行：
  - 并发 5 次签到只成功 1 次，流水 1 条；

- 分支 CI 结果以 GitHub Actions 为准；未合并 PR 按状态说“待复审/待评审”，不说“已合并”。

## 8. 常见提问与答法（2 分钟）

| 老师可能问 | 回答 |
| --- | --- |
| 密码怎么存？ | scrypt + 随机盐，异步计算不阻塞事件循环；只存摘要，登录用恒定时间比较。 |
| 会话怎么失效？ | 不透明刷新令牌存 SHA-256 摘要，15 分钟 access / 30 天 refresh；刷新轮换，检测到重放整链撤销。 |
| 重复提交怎么办？ | `Idempotency-Key` + 服务端 scope：同键同体返回首次结果，同键异体 409。 |
| 并发安全吗？ | 关键路径有真库并发测试：签到、注册、刷新轮换、同步批次、邮箱并发注册/绑定、订单支付。 |
| 数据隔离怎么保证？ | 内容表启 RLS，事务内 `set_config('app.user_id', …)`，应用层再做归属校验。 |
| 表结构谁维护？ | 同事统一维护 schema 与迁移，我提字段建议并实现 API 业务。 |
| **邮箱注册为什么先 verify 拿 ticket？** | 验证码只在 `verify` 时换一次性 ticket；ticket 绑定 purpose + 邮箱、60 秒过期、只消费一次。注册/重置把 ticket 消费和业务写入放在同一事务，避免复用、并发重放和“码已验但账号没建”的中间态。 |
| **订单金额为什么只信快照？** | `products` 是可变配置，可能改价/下架；下单时把标题、单价、币种、积分、VIP 天数写入不可变 `product_snapshot`。客户端只传 `product_id`，支付校验金额/币种都读快照，绝不信任客户端金额。 |
| **重复支付回调怎么处理？** | `payment_events(provider, event_id)` 唯一键 + 订单状态机：同订单重复 event 返回 200 `replay=true`，跨订单复用返回 409；积分/权益只在首次 PAID 状态迁移中发一次。 |
| **提醒怎么保证重启后还在？** | 已调度 requestCode 存 SharedPreferences；启动、保存/完成/恢复、时区变化都 `resyncAll`，BOOT/TIMEZONE/TIME_SET/MY_PACKAGE_REPLACED 由 Receiver 重建；通知权限只在弹通知前检查，调度本身不受影响。 |
