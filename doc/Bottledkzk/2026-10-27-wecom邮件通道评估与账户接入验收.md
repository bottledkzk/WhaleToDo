# wecom-cli 邮件通道评估与账户接入验收

用户提出评估 `WecomTeam/wecom-cli`，作为真实验证码投递的候选通道，并交由账户模块负责人接入。本 PR 只交付已核实的运行条件、接口边界和验收要求；本侧未安装生产 CLI、绑定企业微信账户或发送邮件。

**最新分工确认（2026-10-28 UTC）：用户明确 wecom-cli 正由队友部署，本侧不操作。** 下列主机和安装情况均为评估时快照，不能覆盖队友正在进行的部署。当前安装路径、固定版本、账户权限和交付结果由部署负责人提供；本侧不重复安装、升级、重启、配置或授权，也不另行开通 SMTP 备选。

## 1. 结论与证据

**可以在现有服务器运行，但“能运行 CLI”与“能作为公开注册验证码通道”还需分开验证。** 它通过企业微信云端发送邮件，本身不会提供邮箱账户、SMTP 邮件服务器或我方域名邮箱。

本轮核对的上游源码提交为 `55785fa0a5c922279533a5b5a836b44b56f65ce7`，包清单版本 `1.3.4`，MIT 许可；这是评估快照，不承诺永远为最新版。

## 3. 第一阶段：先做有界投递验证

使用明确可用的发送账户与双方同意的测试收件邮箱，在隔离的私有配置目录完成：

1. 固定安装版本并核实来源/校验，读取版本和授权状态；仅账户持有人完成扫码，运行目录归专用用户所有。
2. 授权后读取实际 `mail --help` / `mail send --schema`；记录邮件权限、实际请求/响应字段、发件身份和额度规则。只保存脱敏schema，不导出其他邮件、通讯录或机器人会话。
3. 向指定的少量外部测试邮箱发送固定“投递联调”邮件，记录服务端接受与收件箱实际到达两项证据、耗时和垃圾箱情况。QQ/163/学校邮箱至少覆盖实际产品需支持的类型；未通过的域不要宣称可用。
4. 验证凭据刷新、权限撤销、限流、网络超时/结果未知；不对发送动作做盲目重试。CLI成功/返回mail_id只算提供方接受，收件人实际到达仍需核验。
5. 输出结论：可用/能力受限/不适合公开OTP，并说明额度和恢复约束。如果无法向目标外部邮箱投递或不适合该用途，保持可替换邮件适配层，另选合适通道；不把产品注册限定为必须先有企业微信账户。

这一步由当前部署／账户负责人执行；本侧未执行，不推断队友当前进度。不会把 dry-run、本地文件收码或仓库支持参数写成真实邮件验收。

## 4. 第二阶段：账户适配器的最小交付

沿现有 `buildApp(... emailCodeSink ...)` 边界接入，保持验证码随机生成、摘要保存、用途/时效、共享冷却、尝试次数、验证ticket原子消费、密码重置与刷新族撤销等现有规则。邮件传输凭据不进入数据库账户权限或AI网关权限。

- 以服务端固定模板生成主题和正文，单次只发送到已校验的目标邮箱；不接受任意subject/body、cc/bcc、附件、可执行路径或自定义CLI参数，避免形成匿名邮件中继。
- 调用固定绝对路径CLI时使用参数数组、禁用shell，限制超时、并发和输出大小。动态schema变化须失败可见，不静默改收件人或降级到其他身份。
- 独立 `WECOM_CLI_CONFIG_DIR`，目录0700，凭据/密钥/临时正文0600；正文文件在最短生命周期内删除，不在命令行参数或日志放验证码。无keyring回退文件与加密凭据同目录时，安全性依赖操作系统权限，不能宣称仅凭“加密”即与服务进程隔离。
- 适配器明确区分提供方已接受、明确拒绝、超时/未知。未配置通道不能返回“已发送”；明确失败应给稳定可恢复提示，不回显CLI原始stderr或正文。未知不能立即重复发送或重新生成验证码规避；保留冷却/限流并提供可核对的脱敏投递状态。
- 认证刷新只处理提供方明确的token失效；发送结果未知时不能因刷新/进程重启自动重发。不要未经核实宣称CLI或提供方有发送幂等保证。
- 当前接口是同步sink，若需独立worker/持久队列，先提交队列、敏感payload生命周期与失败恢复设计；新增schema/迁移由双方评审，不能在现有DB增加明文验证码持久化。
- `ServerProfileBridge.requestCode`目前会明确阻止假送达流程，账户PR须同步更新为真实服务结果，分别显示未配置、限流、失败/未知与已接受状态，避免后端成功客户端仍固定报“邮件尚未接入”。
- 生产默认关闭新通道，先完成受限运行/配额/真实投递验收再按发布步骤启用；不开放新的公网邮箱服务端口、不调整DNS/443或占用现有服务。

建议账户PR同时提供仅包含配置键的示例、启停/撤销说明、失败矩阵和可替换的fake传输；是否使用CLI常驻worker或每次子进程，由资源测量和恢复设计决定，不能仅以平台支持就开启无限并发。

## 5. 可合并与生产验收矩阵

| 层次 | 最小证据 |
| --- | --- |
| 无账户本地检查 | 固定模板/准确收件人；参数数组无shell注入；限时/限并发/输出截断；日志无code/token/邮箱正文；临时文件清理 |
| 故障回归 | 未配置/无权限/限流/刷新失败/断线未知；不谎报sent，不自动新请求重发，不绕过原冷却与OTP验证规则 |
| 实际服务器运行 | 固定版本、专用用户权限、重启/撤销恢复、峰值资源与可回退；不影响既有AI/网站/备份恢复 |
| 真实邮件 | 提供方接受与外部邮箱实际收件分别记录；只留脱敏回执，不公开验证码、完整邮箱或二维码 |
| APP账户闭环 | 请求验证码→实际收件→验证→注册/登录→签到；密码重置与旧会话撤销、换号隔离分别验收 |
| AI闭环 | 在合法账户/余额和已发布网关基础上单独验日记/配文与未知恢复；邮件成功不等于AI/生产发布已完成 |
