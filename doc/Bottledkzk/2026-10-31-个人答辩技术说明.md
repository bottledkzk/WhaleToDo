# WhaleToDo个人技术答辩说明

作者 Bottledkzk　更新 2026-10-31　版本 0.5.4-preview.1

## 个人职责与项目概览

这份材料供Bottledkzk准备软件工程答辩使用，重点说明技术栈如何支撑功能、关键设计为什么可靠，以及现场应该怎样演示。讲解以功能和数据流为主，不要求逐行展示源码。当前交付为0.5.4-preview.1，支付全部为MOCK。

### 可以直接使用的开场

我负责WhaleToDo的整体前端与核心排程、AI Agent、数据库和生产部署，以及官网和签名安装包发行。后续还承接了主动云备份、资料日记同步与MOCK支付链路。队友主要负责认证和网络、邮箱验证码、签到基础、提醒、相机相册与ShareStudio，我们通过接口约定和PR交叉评审完成集成。

这个应用希望把“记下来、安排好、做完、回看和分享”连在一起。访客不用登录就能记录和安排；需要在线AI或账户权益时再登录。我们把任务和具体时间块分开，让一件90分钟的事项可以在约束允许时分段执行；让模型理解意图，再由业务规则计算并校验实际安排，最后由用户确认。

### 答辩中应说明的交付状态

公开0.5.3签名包已经在小米14 Pro Android16上走过基础全流程：访客记录、邮箱账户、资料定制、签到、MOCK收银台、真实AI排程及跨日调整、日记、QQ分享与两种手动同步。0.5.4使用同一证书覆盖升级，补测四种日记风格入口，以及真实生成、编辑确认保存和账户资料同步。

这是基础流程与版本增量分开验证的结果，不能说所有功能在所有手机重新验过。旧体验包、访客记录和历史下载均保留；没有把模拟器、CI或MOCK支付替代真实设备和真实资金证据。

### 个人主线

讲解顺序建议是：应用分层与本地优先 → 排程和Agent的安全落地 → 数据隔离与主动同步 → 账本和MOCK支付 → 部署发行与验证。这样可以沿着一条数据从输入到保存、再到发布的路径解释自己的贡献。

## 架构与技术选择

客户端负责快速交互、离线持久化和领域约束；服务端负责身份、钱包、订单与模型调用的权威状态。两端职责划清后，断网不会阻断基础记录，也不会让客户端自行决定积分或会员权限。

| 层次 | 实际技术 | 解决的问题 |
| --- | --- | --- |
| 界面 | Kotlin与Compose Material3 | 按状态绘制界面，统一主题和五个主要入口 |
| 状态与异步 | ViewModel 协程 StateFlow | 把页面状态与请求处理分开，避免过期响应写错账户 |
| 核心规则 | 纯Kotlin core | 独立测试区间、工时、截止、固定块和排程 |
| 本地数据 | Room2.8.3 schema6 | 本地持久化、owner分区、事务保存与升级保留 |
| 网络 | HttpURLConnection与序列化 | 只访问自有HTTPS API，统一错误与令牌处理 |
| 服务端 | Node24 TypeScript Fastify Prisma pg | 接口校验、账户业务、幂等与数据库事务 |
| 数据和发行 | PostgreSQL16 Nginx systemd GitHub Releases | 权威账本、受限部署、可回退版本与真实下载 |

### 一条数据如何流动

用户输入先成为界面状态，由用例和core规则处理；需要持久化时进入Room，需要在线能力时通过网络桥接调用自有API。账户API和AI网关是两个进程，分别使用受限数据库角色；只有AI网关持有上游模型凭据。官网只是介绍和下载，不承载账户认证。

### 为什么选择这些技术

Compose适合让异步结果直接反映为状态；Room让基础功能不依赖网络；独立core使排程能脱离手机复现。PostgreSQL的约束和事务适合账户、钱包与订单一致性。我们保持课程规模的模块化单体加独立AI网关，没有为了架构名词引入微服务集群。

构建使用JDK21运行Gradle8.13、Java17字节码、Kotlin2.2.21和AGP8.13.2，最低API26、目标API36。最低版本可构建不代表所有Android版本均完成真机测试。

## 排程与 Agent 如何实际落地

### 事项与时间块分开

事项保存标题、预计工时、截止、重要度和完成状态；时间块保存具体起止和是否固定。同一事项可以对应多个时间块，调整一个块也不必改写整个事项。预计工时是预算，完成时刻是另一类事实，二者不能混用。

### 确定性排程的工作

先合并忙碌区间并从可用时间中扣除，再保护固定、已经开始和已完成的安排，根据截止、重要度和剩余预算寻找空闲时段。可拆分事项按允许的时长放入；不可拆分事项不能跨越真实空隙。放不下时保留未安排量，不能越过截止假装排满。

连续工作限制需要跨事项累计。例如上限60分钟、休息10分钟，不能把两个40分钟任务连续放下后称为合规。排程必须把休息实际插进时间线，且各任务工作段之和仍等于预计工时。固定例会的ID与原时段保持。算法是可解释启发式，不承诺全局最优。

### 模型与规则各自负责什么

模型理解“明天上午安排复习、保留例会、工作一小时后休息”这样的意图，提供建议或受限结构化提案；具体候选由领域规则计算并校验。聊天、计划、复盘、日记、配文和编辑使用同一网关，但只有编辑允许返回限定类型的变更。模型不能任意执行工具、SQL或系统命令。

明确的跨日移动会绑定原任务或时间块和用户指定的当地日期，移动保留时长；日期不清楚时询问，不依赖模型猜毫秒。服务端检查结构和权限，本地再检查截止、冲突和保护规则。真正写入发生在用户看过预览并按Accept之后。

### 确认时还要再查一次

预览出现到Accept之间，数据可能已变化，因此提交前重新核对账户、登录会话、VIP、快照和约束，再用Room事务一次应用；失败则整批不写。历史Accept、模型说“已修改”或文字里的授权，都不能替代当前确认。

真实验收曾完成五事项八个工作块，并核验工时、截止、无重叠、固定例会和60／10休息；之后只把散步块跨日移动，其他块不变。这展示了从自然语言、候选校验、人工确认到实际日程写入的完整路径。

## 数据隔离 同步与费用一致性

### 为什么有两套数据库

Room负责设备上的离线工作，PostgreSQL负责服务器权威状态。访客和各账户在Room按owner隔离，登录只切换分区，不把访客日程自动上传或覆盖到账号。退出后原来的五条访客记录仍应存在。服务器从令牌取得身份，不能接受请求体指定另一人的user_id。

| 数据 | 同步方式 | 用户控制 |
| --- | --- | --- |
| 昵称 motto 日记 | 随账户资料同步 | 保留离线差异，字段冲突明确选择 |
| 日程与安排 | VIP主动备份和恢复 | 云端备份后再选择覆盖或兼容并确认 |
| 助手会话 设备偏好 图片本地URI | 保留本地 | 不加入日程或资料云文档 |

覆盖以云端备份替换本地日程；兼容保留本地同编号对象，云端冲突安排不会直接覆盖本地时段。云文档revision用于判断版本变化，打开设置不发送日程GET或POST，兼容结果也不会悄悄再上传。资料同步和日程备份是两条路径。头像相机／相册选择在本机账户资料中保留，不宣称已完成跨设备图片托管。

### AI为什么要先预占

发模型请求之前要原子检查余额并把available移入reserved，防止并发调用超支。成功后按照真实token结算并释放剩余预占；明确失败释放，未知结果保持原请求状态并查询原ID，避免重复调用和重复计费。供应商可能已收费，项目积分释放不能证明上游免费。

费用采用冻结费率桶的累计向上取整：累计成功token决定总应扣，再减去已经扣过的积分。当前起始3200 token对应1积分，目标是按真实任务分布校准到平均约0.5积分；不是每次固定扣0.5。连续三个短请求可能显示1、0、0分，这是累计规则的结果。不同模式的实际消耗也会不同。

### 数据库安全怎么做

值使用参数化SQL，有限标识符走白名单；数据库只监听回环，账户、AI和迁移角色分离，内容归属同时依赖接口检查与RLS。十条迁移只追加、不改旧checksum；备份必须有恢复演练，不能只看到文件就声称可恢复。

## 支付 失败恢复与生产发行

### MOCK也需要完整业务链路

所有账号采用MOCK，界面明确模拟支付，不发生真实扣款。用户选积分或VIP档位，服务端按商品目录生成订单，冻结价格、币种和权益快照，再跳到在线收银台。用户确认本人订单后，支付事件、订单状态和积分／VIP发放在同一事务完成。

取消、返回或冷启动会找回待支付订单，不能因为页面关闭就重复建单。相同确认重放只返回原结果，不再次发权益。客户端的成功回调只触发状态查询，不能直接给钱包加分。真机已验证积分订单取消后恢复、支付到账以及VIP权益生效。

银联沙箱曾取得签名后端订单TN，但真机唤起云闪付未完成支付闭环，所以最终交付选择MOCK。不能把拿到TN写成已实现云闪付真实支付。未来接真实通道还需验签、官方查单、金额币种核对和异步通知恢复。

### 失败路径如何保持可信

错误验证码、旧密码、断网、登录失效、余额不足和模型暂不可用需要分别反馈；邮箱重发有60秒等待。网络结果不确定时查询原ID，草稿重开不重新生成或计费。密码实际采用异步scrypt及随机盐，令牌只存摘要并可轮换撤销；答辩应按实际实现介绍认证技术。

### 从源码到可下载版本

先冻结并评审提交，运行模块测试和构建，用固定发行证书签名APK，记录版本、包名、源码和校验值。先上传GitHub草稿并逐项读回，再公开Release；官网从版本化目录提供同一APK，核验后原子切换，保留历史版本。用户不需要在首页手工算SHA。

网关与账户API可以单独升级。此次日记更新只切换AI版本并重启AI，账户API、数据库迁移和其他服务保持；失败可切回旧目录。凭据只在服务器私有配置，经systemd加载，不进入APK、网页、日志或答辩投屏。备份与恢复已设置，持续清理未启用，也没有宣称自动异地容灾。

## 建议的十分钟演示流程

演示使用专用账号和合成事项。提前确认网络、VIP、余额与当日调用余量，主线预留计划、编辑、日记、配文四次真实调用；聊天只在额度充足时补充。注册和密码重置作为扩展支线，验证码在本人设备处理。不要在投屏展示密码、令牌或私有运维页面。

| 时段 | 操作 | 对应技术亮点 |
| --- | --- | --- |
| 0:00–1:20 | 访客记下事项，补工时截止，固定一项，自动安排并查看预览 | 本地优先、事项与时间块、固定保护 |
| 1:20–2:20 | 登录，展示头像昵称motto和7日签到 | 账户分区、受控错误、服务端账本 |
| 2:20–3:10 | 选充值档，跳MOCK收银台确认，再看余额和VIP | 订单快照、幂等、真实持久化 |
| 3:10–5:40 | 输入复杂约束，核对计划预览后人工Accept | 模型理解、确定性排程、事务落地 |
| 5:40–6:40 | 只把一项移到下一天，检查其他项后Accept | 日期与原对象绑定、时长保护 |
| 6:40–7:40 | 完成一项，选日记风格，编辑确认保存 | 真实完成事实、自然正文、资料同步 |
| 7:40–8:40 | 生成分享配文，卡片预览并保存或选QQ | PNG、URI授权、草稿恢复和显式分享 |
| 8:40–10:00 | 手动备份，预览覆盖／兼容，退出回访客 | 同步选择、revision和访客记录保留 |

### 可复用的复杂排程输入

把示例日期改为演示当天之后的有效日期：09:00–18:00可用；算法复习90分钟，12:00前完成；答辩彩排45分钟，17:00前完成；材料整理30分钟，散步20分钟；固定例会11:30–12:00；工作60分钟休息10分钟。先准备真实事项，再让助手安排并核对预览。

失败时不硬演成功：尚未返回就查询原ID；配额不足就展示历史结果并说明；同步等待前台协调周期。不要为了现场速度关闭验证或自动点Accept。QQ已发送的合成卡片可展示记录，不必反复外发给队友。

## 个人讲解稿与常见问题

### 两分钟技术讲解稿

我把WhaleToDo分成了交互、领域规则、本地数据和在线服务几层。Compose用状态绘制界面，Room保存离线记录，core专门计算时间安排，所以没有账号和网络也能完成基础流程。任务和时间块分开后，工时预算、固定例会和分段工作可以独立处理。

AI这一层我重点解决的是建议怎样变成可靠的操作。模型理解用户诉求，本地规则生成并检查具体安排；服务端和本地分别验证，用户看过预览后按Accept，才在一个事务里写入。对于明确跨日移动，绑定原对象和当地日期，避免调整错任务或错天。

在线部分以PostgreSQL保存账户、钱包和订单。调用先预占、完成后按真实token累计结算，不确定结果查询原ID。日程只允许VIP主动备份和覆盖／兼容同步，昵称motto日记才自动跟随账户。支付采用MOCK，但订单恢复、确认和权益幂等都实际经过服务器。最后用固定证书、Release附件读回和网站版本目录把可运行成果交付出去。

### 为什么不让模型直接输出最终日程并保存

模型会误判日期、漏约束或算错分钟。把时间计算交给可测试规则，再保留结构化校验和人工确认，可以分清语言理解与业务正确性，也便于解释失败原因和复现。

### 如果用户在预览后又改了任务

Accept前重新检查快照、归属和约束。预览不是长期有效的授权，旧预览应拒绝并重新生成，整批事务不会写一半。

### 为什么登录后没有自动出现所有云日程

这是明确的产品选择：登录只切换账户分区。用户主动备份和选择覆盖／兼容方式，防止设备上的安排被无提示覆盖；个人资料与日记采用另外的同步文档。

### 如果模型超时是否立即退款和重试

只有明确失败才能按失败路径释放。超时可能是结果已产生但客户端没收到，必须查询原ID；否则既可能重复扣费，也可能生成互相冲突的操作。

## 可证明的特色与如实说明的边界

### 日记是否只靠提示词

提示词规定事实与四种表达风格，服务端还校验JSON正文、报告式布局和独立注释，针对真实样例中出现过的虚构心境、次数和模糊时刻补有限守卫。它不能证明任意语义都真实，所以生成后继续提供预览、编辑和确认保存，不把“模型返回成功”当成质量成功。

### MOCK为什么仍有工程价值

因为交易一致性不是支付SDK独有的问题。目录、订单快照、恢复、状态机、事件去重、钱包和VIP一次发放都能在MOCK中实际验证。真实收单的验签、资金和商户条件尚未实现，必须单独声明。

### 为什么积分有时扣零分

同一费率桶按累计token向上取整，当前累计应扣可能没有超过此前已扣值。本次零分不是没调用模型，也不是供应商免费。换算目标看平均任务分布，输入长度和模式变化后仍需复核样本。

### 两个人的工作怎样说明

我讲前端、排程、Agent、数据库部署、主动同步、MOCK支付与发行；队友讲认证网络、邮箱、签到基础、提醒和媒体分享。原始贡献和后续接手分别说清，接口和迁移经交叉评审，不用提交次数推算贡献，也不代写对方设备测试完成。

### 哪些说法应避免

不说“AI完全不会出错”“排程全局最优”“所有Android都已测试”“云闪付已实现真实支付”“所有社交平台已通过”“已经自动异地容灾”。可以说：当前范围有可复现规则、真实服务和签名包真机证据，剩余矩阵与非阻塞改进清楚列出。

### 当前仍应继续做的事

队友本人手机需补齐通知锁屏、后台、重启、省电和媒体权限矩阵；共同关注多端并发及长期运行。非阻塞的日记语义检查和触控细节可以继续改善。真实收单、专项平台SDK和长期多阶段模型不属于本轮必须补出的承诺。
