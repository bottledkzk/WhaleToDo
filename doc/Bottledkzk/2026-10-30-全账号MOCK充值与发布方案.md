# 全账号 MOCK 充值与发布方案

项目发起人本轮明确决定：“对所有账号，都使用MOCK，均是MOCK”。本方案替代此前仅独立演示环境启用 MOCK 的限制。PR54 已评审合并；此次是新的全账号产品策略及生产部署配置变更，需要按共享变更流程交叉评审。

## 行为

- 保留 NODE_ENV=production、现有受限 PostgreSQL、登录会话和持久幂等密钥
- 显式 PAYMENT_PROVIDER=mock 时，全部普通登录账号可创建并确认本人的模拟订单；disabled 为关闭/回退模式，真实支付未接入
- 客户端继续经过“创建模拟订单 → 确认模拟支付”，标明无真实扣款；确认后积分与 VIP 在当前账号生效
- 服务器仅从原订单快照取金额、币种及权益，不接受客户端自行指定积分/VIP；同单并发及重放只发放一次
- 生产不注册旧的 /payments/mock/webhook；旧 test/demo webhook 禁止占用 checkout: 事件前缀
- 在原八条后顺序追加 `202610300002_mock_catalog`（VIP7/30天、100积分）和 `202610300003_payment_tiers`（20/500积分、VIP90天），合计十条迁移、六档；两条均 ON CONFLICT DO NOTHING，不覆盖自定义商品或既有订单快照，原八条 SQL 未修改

## 验证

完整服务端单元/HTTP检查及 strict tsc 通过；普通 verification 构建通过。服务器新的临时 PostgreSQL 集群 93/93：包含生产模式 HTTP 下单/并发确认、受限 PG 持久账本、他人订单拒绝、价格/权益变化后按旧快照发放、生产 webhook 404、目录迁移幂等且保留自定义价格。验证集群独立目录/端口/角色，结束停止并清理；生产 API/AI/nginx/xray 进程均保持，生产迁移未应用。

生产上次发布验收记录为 f3d1fa7 / 八条迁移 / disabled，本 PR 不代表已经切换生产。之后已在独立验收后端和独立 verification 包完成档位、在线收银台、取消/冷启动恢复及确认流程，结果见 PR 验收说明；这些不替代正式部署回执，公开 APK 未更新。

## 评审后发布顺序

1. 冻结经交叉评审的提交，构建发行包；保留现有受限凭据，不使用 demo 账户或内存仓储
2. 备份 → 临时恢复库从八条顺序执行 0002 → 0003，核对完整十迁移边界及六档商品 → 校验旧表既有列数据、迁移历史、角色/RLS → 生产备份/门禁/迁移
3. 切换经过验证的 API 源码，并为 API 明确设置 PAYMENT_PROVIDER=mock；仅重启 API，保持其他服务与密钥配置
4. 检查 ready=available、payment_provider=mock、商品目录及客户端模拟标识
5. 由真实测试账号显式创建/确认一笔小额模拟积分订单和一笔 VIP 订单，核对服务端账本、重开恢复与重复确认；金额只作模拟展示
6. 后续备份恢复检查，再构建包含 PR56/57/本 PR 的公开候选版本并分别记录设备与发布结果

关闭充值时改回 PAYMENT_PROVIDER=disabled 并重启 API。保留已产生的订单、事件、积分账本及 VIP 审计记录，不通过删除记录回退。

## 模拟权益与调用边界

项目决定仍为全账号 MOCK，不恢复白名单或“仅当前演示账号”的旧限制。页面使用简短“模拟支付 · 无真实扣款”、模拟渠道和“模拟支付成功”；展示金额不发生资金结算

模拟积分和 VIP 按本人订单进入同一权益账本，可用于真实 AI。已确认接受这一演示产品选择；真实模型仍受服务端按账号/全局调用次数、token 上限和供应商余额保护约束，不能把 MOCK 余额当作绕过模型限额的凭据

单进程 API 另按账号限制：新订单 30 次/分钟、收银台读取 120 次/分钟、待支付确认 30 次/分钟。已有幂等下单回执和已支付订单重放仍可查询/恢复。此为 HTTP 防刷，不是持久财务额度；多实例须替换为共享限流，生产显式核对 AI 持久预算配置

正式边界为 FULL_BOUNDARY=202610300003_payment_tiers / count=10；gateway 仍为八条且禁止启动账户 API。恢复演练须验证 0002+0003 顺序、六档默认值、重复执行不改自定义价及订单快照，不能仅演练九条

发行包内 `DEPLOYMENT.md` 使用本说明，避免携带历史七迁移指引。网站打包默认保留现有公开 GitHub 版本作为备用入口；先确认同版本 Release 已公开，再执行 `python script/package-website.py <新的产物目录> --public-release-tag v0.5.3-preview.1`，使主下载与备用入口一致。参数必须匹配 APK 元数据，已生成归档不得覆盖；旧版公开附件及下载目录保留

本次产品决定对 VIP 持续开放 Agent 编辑，仍保留预览后人工 Accept、按账号与全局调用/token 限额及供应商余额保护。生产须显式设置 `AI_EDIT_ENABLED=true`；MOCK 权益不绕过调用限额。发布回执分别记录 API 和 AI 的切换结果，不把代码合并当作已经上线


## 收银台恢复与切号回归

`CashierRecoveryIsolationTest` 默认运行实际 Activity 重建/切号关闭及设备回执读写隔离（合成 API，不连接支付或模型）。跨进程回执测试分两次 instrumentation 调用同一 `pendingReceiptSurvivesNewStoreAndColdStart` 方法：第一次传 `payment_phase=save`，完成后强停 verification 包，再以 `payment_phase=restore` 调用；restore 校验原 product/key/order/时间与 owner/backend 隔离并清理合成回执

桥接单元覆盖打开页面后切号、校验期间切号、错误 product/order 在 POST 前拒绝、重开桥接查询原单不重建，以及支付回复丢失按原订单恢复。账号变化会关闭旧 CashierActivity；不会继续读取 A 订单或把 A 权益写入 B。上述新增标准模拟器/单元结果与此前真实手机/独立服务验收分别记录，不代表生产已升级


T93 增补的跨进程自动复测入口（先安装配套 verification 应用与 AndroidTest APK，再在仓库根目录执行）：

```powershell
./script/test-payment-cold-start.ps1 -Serial emulator-5580 -Adb adb
```

该脚本实际分两次 instrumentation 调用，中间强停独立验证包；任一阶段没有 `OK (1 test)` 即失败，不把默认 roundtrip 当成跨进程证据。只使用专属合成偏好，不清数据、不创建订单、不调用模型或付款。另有 HTTP 回归验证既有 31 笔 PENDING 中前 30 次确认通过、第 31 次 429、已 PAID 重放仍成功且不重复发放；客户端 PAID 预检只做一次权益/钱包刷新而不 POST
