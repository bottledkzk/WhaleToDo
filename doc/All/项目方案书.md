# WhaleToDo 项目方案书

版本：0.2　更新：2026-10-22　用途：团队同步、后续分工实施与软件工程答辩。本文描述目标方案，未实现项不视为已交付。

## 1. 产品与范围

WhaleToDo以Android APP为主，将快速记录、直观Todo分布、自动协调、提醒、打卡复盘、AI辅助和自主分享连成日常使用流程。配套网站承担介绍与下载，账户服务器承担身份、同步、积分、权益、订单和模型网关。

本地基础能力允许访客与离线使用；AI必须登录，由服务器持有供应商凭据并转发请求。免费用户每日签到领取积分获得调用额度；VIP可获得更多积分或功能权限，具体数值与权益后续设定。用户不能导入自己的API Key，也不能把客户端设为绕过登录的模型代理。

分享支持少量固定图片样式、相册／相机选图、保存图片和可编辑AI配文；面向QQ、微信、动态／朋友圈、微博等，以实际客户端与官方能力为准，不自动发布。

完整功能、数据边界及验收见 [目标功能文档](目标功能文档.md)。

## 2. 总体技术方案

Android采用Kotlin＋Compose＋ViewModel／Flow＋Room，独立core模块实现规则与排程。客户端负责交互和本地约束，服务器负责身份、私有对象授权、积分／订单权威状态和外部模型调用。

后端先保持一个可启动服务＋PostgreSQL，语言／框架在实现前由两人确定并固定。网站与API按职责部署，通过可信HTTPS域名提供服务；数据库和管理入口不直接暴露公网。当前服务器和域名尚缺，后续补齐，本地服务和模拟接口仅用于开发。

AI修改安排采用受限结构化提案、数据版本校验、预览确认和事务写入。聊天不能授予管理员权限，也不能直接修改积分或VIP。设计见 [架构与技术栈](架构与技术栈.md)、[接口与数据契约草案](接口与数据契约草案.md)。

## 4. 账户、支付与安全

只采集必要资料，密码使用成熟哈希库，令牌可轮换和撤销。所有私有对象服务端检查归属；客户端按钮和本地VIP标志不作为权限依据。签到和AI消费采用唯一约束、事务与幂等请求，防止重复奖励、透支和重复扣分。

支付按课程规模先做显式模拟通道、订单状态机与VIP权益，不发生真实资金往来。真实支付需服务器核验通知和订单金额后幂等发放，不相信客户端返回“成功”。积分数、套餐、VIP具体权限和真实通道后续决定。

部署必须考虑HTTPS、最小权限、私有数据库、密钥隔离、日志脱敏、限流、费用上限、备份恢复和可回滚版本。详细流程和安全验收见 [账户、AI积分与安全方案](账户-AI积分与安全方案.md)。
