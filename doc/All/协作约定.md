# 协作约定

## 文档边界

`doc/All` 是团队共用基线，范围／接口变更通过PR评审；个人每日记录放本地外层report和plan，需向团队汇报的结论再整理进对应成员目录。

`doc/Bottledkzk` 与 `doc/Weiding` 是对团队可读的成员材料，不自动代表成员认领任务。成员自己的成果由本人核对后确认，不伪造他人提交或汇报。

## 认领模板

| 字段 | 内容 |
| --- | --- |
| Issue与功能ID | 例如F03：可用时间与排程 |
| 负责人／评审人 | 待本人确认 |
| 输入／输出 | 界面、用例、数据和接口边界 |
| 依赖 | 前置功能、环境、账号和服务 |
| 验收 | 可执行命令、设备场景及证据 |
| 状态 | 未认领／进行中／待评审／完成／受阻 |

建议按“核心与数据、客户端体验、AI与服务、质量与发布”等职责包讨论。两人可以合并职责，但不在未讨论前给Bottledkzk或Weiding固定派工。

## Git流程

主分支main，短功能分支后经评审合并；紧急修复也保留测试说明。提交采用`docs`、`chore`、`feat`、`fix`、`test`等类型，说明实际成果。不要提交空改动、生成缓存、凭据或测试账号。较大功能拆成可理解、可构建或可独立验证的阶段，而非逐行凑提交数。

建议PR说明：问题与改后行为、涉及模块、验证、截图与限制。负责人和评审人由成员确认，不直接授予未知账号访问权限。
